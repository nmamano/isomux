# Asks

Task fd794190. Design agreed with Nil on 2026-10-18; the mocks Nil approved are in the lane b1034 report.

An ask is a prompt from an agent to one member, for what the agent needs from them to get unblocked. It stays above the agent's chat input for that member until the member replies or dismisses it, so the agent does not repeat the question and the question does not get lost under later messages.

## Store

- `server/asks.ts` keeps the open entries in `~/.isomux/asks.json`, an array of `{id, agentId, memberUserId?, prompt, createdAt, updatedAt, link?, options?, recommended?, commands?, editFiles?, readFiles?, secret?}`. The load check admits three shapes: a plain ask and a personal secret request name one member; an office secret request names none, even when it is for one owner (see "Secret requests"). Closed entries are not kept: a reply, a dismiss, a filed task, the agent's delete, or the agent's removal deletes the entry.
- A missing file is an empty list, so an office from before this feature boots unchanged. A corrupt file is moved aside; an unreadable one makes the store refuse every call (the pager store's posture).
- Every change writes the file first and changes memory after.
- Bounds: a prompt is at most 4000 characters; an agent has at most 50 open.

## Routes

The agent manages its own list on `/api/agents/:id/asks` (`self:affordance` and `agentParamMustEqualTokenAgent`, so a token reaches only its own `:id`; an entry of another agent is a 404 on its own path). Create and edit take the text/plain form (`shared/plain-text-form.ts`), or a JSON body whose prompt is `text` or its alias `prompt` (task 26e78c4c; both is a 400); create takes `member=<username>`, default the agent's manager, and the member must reach the agent's room.

Create and edit take an optional `link` to an office page (task 3ea6fdb3): one of `OFFICE_LINK_PATHS` in `shared/office-links.ts`, the canonical path of each UI page and `/integrations/<tab>` for each Integrations tab. The page and tab lists live there, and `ui/routes.ts` and the Integrations page read them, so a new page or tab is a target with no second list. The tab forms are also URL routes, accepted at load and rewritten to `/integrations` (task df206fe3); the agent form `/agents/<agentId>` is also accepted at load: it opens that chat and the address is rewritten to `/` (task 680747d8). The handlers check the link on write (422 `invalid_link`); the load check takes any non-empty string, so a target a later release drops cannot quarantine the file, and the card draws no link it does not know. On edit an absent `link` keeps it and `""` removes the key. A secret request never has a link.

A link can also name an agent's chat as `/agents/<agentId>` (task 9aaec0eb; `askLinkFor` parses both forms). On create and on an edit that sends it, the handler checks that the agent exists and that the ask's member can reach its room (422 `invalid_link`). An edit that does not send the link does not check it again, so an agent that later moves or goes keeps its link; the card then draws no button for an agent the UI does not have.

Create and edit take optional `options` (task ec730d2f): 2 to 4 answers the member can tap, each trimmed, non-empty, at most 80 characters, no two the same (`checkOptions` in `server/asks.ts`, 422 `invalid_options`). The text/plain form takes one `option=<text>` per option, a list parameter of `shared/plain-text-form.ts`. As with a link, the load check takes any non-empty list of non-empty strings, so a bound change cannot quarantine the file; on edit an absent `options` keeps them and `[]` (or a lone empty `option=`) removes the key. A secret request never has options.

An ask with options can mark one as the agent's recommendation (task d608a5be): `recommended`, the option's text, trimmed and checked against the options on write (`checkRecommended`, 422 `invalid_options`; the text/plain form takes `recommended=`). The mark goes with the options: on edit, sent options without `recommended` clear it, removing the options removes it, and `recommended` alone is checked against the kept options, with `""` removing it. The load check wants only a non-empty string on an entry with options, so a mark that names no option loads, and the card ignores it.

Create and edit take optional chat affordances (task dc79ace0): `commands`, `editFiles` and `readFiles`, at most `ASK_AFFORDANCES_MAX` (10) in total, counted on an edit with the lists it keeps. The text/plain form takes `command=`, `editFile=` and `readFile=`, list parameters like `option=`. Each item passes the chat route's own check (`server/affordance-checks.ts`, which `emitAgentTerminalCommand`, `emitAgentEditRequest` and `emitAgentReadFile` call too). The checks return a refusal kind, and the chat turns it into a system line while the ask routes turn it into 422 `invalid_command` / `invalid_edit_file` / `invalid_read_file`, or 403 `forbidden_path` for a credential store. A malformed list, an empty list on a create, or more than 10 is 422 `invalid_affordances`. Every item is checked before the read files are copied into the agent's files dir (`copyAskReadFile`, the copy the read-file chip uses), so a refusal makes and changes nothing; a copy failure after an earlier copy can leave an orphan, which a prune collects. The entry stores the resolved form: the command trimmed at the end, `{cwd, path}` per editor file, and the copy's attachment per read file. An open ask's copies are owed like a queued message's attachments, so `queuedAttachmentsByAgent` in `server/isomux-office.ts` names them to the attachment prune. On edit an absent list keeps it and `[]` (or a lone empty value) removes the key. A secret request never has them.

The member answers on `/api/asks/:id/reply`, `/dismiss` and `/file-task` (`agent:converse` or `api:send-message`, `memberScope`). One function, `askVisibleTo` in `server/asks.ts`, decides who sees and answers an ask, from live state: the target member, or for an office secret request its named owner or else every office owner, and only while that member can reach the agent's room. `GET /api/asks`, the `ask_*` push, the answer routes and the secret request routes all call it. On the ask routes anyone it refuses gets the 404 of an unknown id; on a secret request's save and decline routes, 403 `forbidden`.

The entry stores the agent's session when it opened the ask, for the reply note. No route or push sends it: `askMemberWire` in `server/asks.ts` drops it from the agent routes, `GET /api/asks` and `ask_upserted` (task 26dd1857).

## The answer

A reply, a dismiss or a filed task goes through `agentManager.sendMessage`, the path a typed member message takes, with `opts.ask` (`sendMemberMessage` in `server/isomux-office.ts` wraps it for the chat, API-token and ask sends). So it wakes or resumes the agent the same way and is refused only where a typed message is, with the same status and code. The ask closes once the message is accepted, which means its echo is durable or it is in the queue; a refused message leaves it open, and a failure after acceptance (a wake or backend error) closes it, as a typed message leaves the composer. Two differences from a typed message:

- It is never a slash command and never the answer to a pending prompt: it skips the typed-choice claim, and while the agent is busy or parked on a two-step prompt it waits in the queue. When the member's answer ends a prompt on an idle agent (/model, /effort, /resume, a cronjob choice), `sendMessage` flushes the queue, since no turn end does; a permission prompt ends inside a turn, whose end flushes it.
- The agent reads `[Member] [Reply to your ask <id>: "<whole prompt>"] <text>`; a dismiss says `Dismissed your ask` and the text is `Dismissed`, or the reason the member typed in the reply field (`text` on the dismiss route; a blank one is a bare dismiss). The `user_message` log entry carries `metadata.ask: {id, prompt, dismissed?, taskId?, sessionId?, options?, recommended?}` (the whole prompt; the options and the recommended one when the ask had them, for the chat), and the queued item carries the same field, so the note survives a restart in the durable queue.

A filed task ("Not now; file as a task", task 2bb653b7) files a task in the agent's room before the message goes, so the message can name it: no priority, no assignee, the member as creator, the title from the prompt's first line and the description from `askTaskFields` in `server/asks.ts` (the prompt, the options, the link, the commands and files, the member's note, and the ask it came from). The agent reads `[Member] [Your ask <id> is now task <taskId>: "<whole prompt>"] Not now; filed as a task`, or the note the member typed in its place. A refused or failed message deletes the task and leaves the ask open, so a retry files one task. Reply, dismiss and file-task share one in-flight set, so a second answer of any kind gets 409 `ask_busy` and files nothing.

## Step asks

A step ask (`server/step-asks.ts`, task c71cb60f) is a plain ask with `step`: a step on the Integrations page that is not a typed value (a provider sign-in, an MCP OAuth sign-in, a browser pairing, a room's GitHub link). The agent sends `step` on the ask create, without `link`; `check` refuses a step that is malformed, that the member may not do, or that is done (409 `step_done`), completes it (the manager as an MCP server's owner, the agent's room for a GitHub link) and gives the link to the step's tab. The step and link are fixed: the edit refuses both. The member can still reply, dismiss or file it.

One predicate per kind reads the current state (a connected account for the member and scope, a signed-in OAuth server, a paired browser, a linked room). The create uses it, and `reconcile` closes every open step ask whose predicate holds, settling each once (the ask's removal decides) with a system line and an office notice (`emitAgentStepAskDone`, metadata `stepAskDone`). The hooks call `reconcile` and say only that something changed: every `provider_accounts_updated` emit, the MCP OAuth callback, a browser pairing, a saved GitHub link, and the boot after the agents are restored. A predicate that throws leaves its ask open. The load check takes any non-empty step kind, so a later release's step loads and never closes itself here.

The ask card's link button passes the step as the link's `focus`; the Integrations page opens the step's tab, switches the personal card to the member the step is for, and marks the setting (`data-step-focus`, `ui/integrations/step-focus.tsx`).

## Secret requests

A secret request (`server/secret-requests.ts`, `POST /api/agents/:id/secret-requests`) is an ask with `secret: {requestId, scope, name, hosts, form, reason, app?, ownerUserId?, answerUserId?}`; the prompt is the reason. The ask is the only record of an open request, so it survives a restart. It never holds the value: the save body goes to the secret store only.

- A personal request is for the member in `memberUserId`: the agent's manager when it opened, or the member the agent named (task 315a62c0). It saves into the secrets of `ownerUserId` (the manager, or the app's owner for an app request; a request from before the field saves into `memberUserId`'s). An office request has no `memberUserId` and is for the owner in `answerUserId`, or every office owner when it names none, while they can reach the room; the first save or decline closes it for all. The named owner is not in `memberUserId` because an older server's load check refuses an office request with a member and would quarantine the whole file after a rollback. The answerer must be allowed to write the target secrets (that member, or an office owner): checked at open (403 `member_not_allowed`) and live in `askVisibleTo`.
- A request can be for a variable or an MCP server instead (`kind: "variable" | "mcp-server"`, task c71cb60f). The type is a union on `kind` (`shared/types.ts`); a secret has no `kind` on disk. The new kinds stay in `AskEntry.secret` and keep `hosts: []` and `form: {kind: "authorization"}` on disk, so an older server loads them as secret requests after a rollback: a masked form that saves into the wrong store, never a reply box that would put a value in the chat. Every rule here that keys on `secret` covers them. The load check takes any other non-empty `kind`, as it takes any link, so a kind from a later release cannot quarantine the file after a rollback: such a request's save is 409 `request_unsupported` (the ask stays), its card offers Decline alone, and a decline or the agent's delete closes it (`knownValueRequest` in `shared/types.ts`). A variable request saves `{value}` through `writeVariable`, an MCP server request `{url, secret}` through `writeMcpServer` (`server/connection-writes.ts`), the same functions the Integrations routes call, so the after-effects match. The open refuses a variable or server that exists in the target scope (409 `variable_exists`, `mcp_server_exists`), and so does the save. An MCP server request's `url` and `secret` are proposals; the open checks that a proposed secret exists in the target scope, not its host, since the member can change the URL. No line, answer or log holds a value or a URL.
- An app request (`app: {name, createdAt}`) has no hosts. Its save re-checks that the app is the same registration and, for a personal request, still the owner's (409 `app_gone`, the ask stays), and gives the secret that app's grant.
- The member answers on the secret request's save and decline routes. A reply, dismiss or filed task gets 409 `secret_request`, so a value typed there never reaches the chat or the agent. The agent's edit gets the same 409; its delete withdraws the request.
- The save creates the secret, then removes the ask, with no await between the permission check and the removal. If the removal fails, the agent is still told, since the secret exists. A decline removes the ask first and tells the agent only after that.
- The chat shows the agent's call and a system line with the outcome. The agent gets the same line, in English, as an office notice (`QueuedMessage.notice`): its sender is the member who answered, so the turn and the usage cap are that member's, but the agent reads only `[Isomux: <line>]`, and its delivery writes no chat entry. The queue strip leaves notices out. A `secret-request` log entry from a server before this change draws a read-only card: its outcome, else closed.

## UI

- The store slice `asks` is filled by `useAsksSync` (`GET /api/asks` on each hydration epoch) and kept live by `ask_upserted` and `ask_removed`, which only the sockets of members `askVisibleTo` admits receive.
- `ui/log-view/AsksStack.tsx` draws the stack above the input: open by default on a desktop, collapsed on a phone, 240 px high on a desktop and 45% of the viewport on a phone before it scrolls. Each card is `ui/log-view/AskCard.tsx`, which the Inbox's Asks tab draws too, so a new kind of ask goes in the card; a secret request draws through `SecretAskCard`. The reply draft is kept per ask in the store (`askDrafts`) until the ask closes, so it outlives the card. While the field holds the untouched default, focus and click select it. Tab and Shift+Tab move between the reply fields of the stack or the Asks tab. A queued answer shows the ask line, as the sent one does.
- The Inbox's Asks tab (`/inbox/asks`, `ui/components/AsksView.tsx` inside `ui/components/InboxView.tsx`; `/asks` still opens it) lists the member's open asks grouped by agent, the longest wait first; the agent's name opens its chat. The tab count and the Asks share of the Inbox entry's badge (office bar and chat bar) count the same list (`ui/inbox.ts`), except that the chat bar leaves out the asks of the chat's agent, which its stack shows (task 1344003f). All show only the asks whose agent is in the agents slice (`visibleAsks`). `GET /api/asks` filters on room access, but an agent in a room the member hides never reaches the client, so its asks stay off the tab, as they stay off the desks. On the Asks tab an answer (Reply, Dismiss, file as a task) waits `ASK_UNDO_MS` (5 s) as a line with Undo, which brings the card back with its draft (task 33939730); the card sends it at once on unmount, on `pagehide` and on `visibilitychange` to hidden, with `keepalive` up to 60 000 body bytes. From the answer on, the store's `answeredAsks` marks the ask, and the counts, the desk dots and the chat stack leave it out (`openAsks`, so the count is `visibleAsks` less those); Undo clears the mark, and the line goes when the answer is sent (task ab332fb2). A send that fails clears the mark and keeps the error in `askErrors`, so the card shows it wherever it draws next. The chat stack and secret requests send at once.
- The desk shows a count dot on the nameplate's corner (`DeskUnit`), and a back-room agent the same dot on its smaller plate (`BackRoomScreen`); the trap door shows no count. Desk rows step 60 scene units vertically, so the front dot (7 units above the plate) stays clear of the plate behind it at any scale; in the back room the nearest plate above is a table behind, about 34 units higher, and the dot reaches 5.
- An ask with options has a button for each between the prompt and the reply field. A tap puts the option text in the reply field (the ask's draft) and focuses it; the member edits it or sends it as it is, so the agent reads it as a typed reply (task 270c4be9). The field starts with the recommended option, whose button carries a "Recommended" tag, empty for options without one, and with "done" only for an ask without options (task d608a5be). The same value is the untouched default that focus selects and that a dismiss does not send as a reason. A ref in the card lets one answer through at a time; the server's in-flight set refuses a second request for the same ask (409 `ask_busy`) and a closed ask is a 404.
- An ask's read files, editor files and commands draw under the prompt, in that order, through the chat's own `FileViewCard`, `EditRequestCard` and `TerminalCommandCard`. Their buttons dispatch `open_in_editor` or `copy_to_terminal` for the ask's agent, which set the pending path or command in the store (`pendingEditorPaths`, `pendingTerminalCommands`) and open that agent's side panel; LogView reads both from the store and the panel clears each once it has used it. On the Inbox the click also opens the agent's chat. With the office's editor or terminal off, the path or command shows as text.
- An ask with a link has an "Open <page>" button under its prompt. App provides the opener (`OfficeLinkOpener`, `ui/office-link.tsx`): it opens the page on top of the chat or the Asks page, so Close and Back return there; the ask stays open. For an agent link the button names the agent, and the opener closes every page, selects the agent's room and opens its chat.
- Every card, a secret request too, has a "Discuss in chat" button (`ui/log-view/AskAboutButton.tsx`, task 715ab3dd). It dispatches `prefix_draft`, which puts `About your ask "<excerpt>": ` (catalog `asks.aboutPrefix`) in front of the agent's chat draft, once, and sets `pendingComposerFocus` to the caret after the prefix; LogView's effect focuses the composer there inside the click (a phone opens the keyboard only for a focus in the tap) and clears the request (`composer_focus_handled`) even when the composer is not mounted. The excerpt (`askExcerpt`, `ui/log-view/ask-about.ts`) is the prompt on one line, cut to 40 code points at a word, with an ellipsis. The member sends a normal message, so the ask stays open; the agent reference tells the agent to answer it in the chat. On the Inbox the button also opens the agent's chat.
- In the agent's chat, an answer shows a one-line "Ask" link (`ui/log-view/ask-link.tsx`). A click on "Ask" scrolls to the "Create ask" card whose result holds the id; without that card the label is text. When the line cuts the prompt, or the prompt has more lines or options, a click on the prompt shows it whole with its options under the line, and a second click folds it.
