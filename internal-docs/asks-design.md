# Asks

Task fd794190. Design agreed with Nil on 2026-10-18; the mocks Nil approved are in the lane b1034 report.

An ask is a prompt from an agent to one member, for what the agent needs from them to get unblocked. It stays above the agent's chat input for that member until the member replies or dismisses it, so the agent does not repeat the question and the question does not get lost under later messages.

## Store

- `server/asks.ts` keeps the open entries in `~/.isomux/asks.json`, an array of `{id, agentId, memberUserId?, prompt, createdAt, updatedAt, link?, options?, recommended?, priority?, commands?, editFiles?, readFiles?, runs?, secret?, step?, app?, simplifyRequestedAt?, originalPrompt?}`. The load check admits three shapes: a plain ask and a personal secret request name one member; an office secret request names none, even when it is for one owner (see "Secret requests"). A reply, a dismiss, a filed task, a step done, a secret request's save or decline, the agent's delete, or the agent's removal deletes the entry from the file; the closed ask is kept in the history (below).
- A missing file is an empty list, so an office from before this feature boots unchanged. A corrupt file is moved aside; an unreadable one makes the store refuse every call (the pager store's posture).
- Every change writes the file first and changes memory after.
- Bounds: a prompt is at most 4000 characters; an agent has at most 500 open.

## Shared asks

Task 9461c464. A plain ask can be for several members: `member` as a list (1 to 20, case-insensitive, no repeats) or repeated `member=`, or `room: true` (`room=1`) for every member who reaches the agent's room and does not hide it (room view level "hidden"). The entry keeps `memberUserId` as the first member and the rest in `otherMemberUserIds`; a room ask has `room: true` and a `memberUserId` picked once at create (the manager when in the audience, else the lowest audience id). An older server's load check reads known fields only, so it loads either as a plain ask to `memberUserId`, and its writes spread the entry, so the keys survive a rollback. The load check refuses a list with `room`, either without `memberUserId`, and either on a secret, sudo, step or reply draft.

`askMemberIds` in `server/asks.ts` is the one read of an ask's audience (an office secret request has its own): the named members, or the room audience read live (a member who joins or shows the room gets the ask; one who hides it loses it). `askVisibleTo`, the wires (`members`, the current names, with `member` its first), the close record and the `ask_removed` push all go through it. Named members, the manager by default too, are not filtered by hidden: the agent chose them (task fec238bf took back 3277082b, which filtered them). A room ask is never in the owners' view of other members' asks, so an owner who hides the room does not get it back there. Under a room-limited token the room audience is empty outside the token's rooms.

The create refuses a list or `room` with `step` (422 `invalid_members`), a bad list or `room` value, and `member` with `room`; a room ask with no audience is 422 `no_audience`. The sudo and reply-draft routes refuse a list or `room` (422 `invalid_members`). The edit takes neither. A link to an agent's chat must be reachable by every member, on create and on edit. A room ask whose audience empties after create stays open, counts toward the agent's open asks and reads `members: []`.

The first answer closes it for all; the in-flight set is per ask. A later answer from a member it was for gets 409 `ask_closed` with `by`, the closer's current name (the close record and `ask_history_members`). `ask_removed` carries `by` to sockets of members who reach the room, other than the answerer's; a room ask's removal goes to every signed-in socket, since a member who hid or lost the room may still hold the card. The client keeps an `answered-first` result in `askResults` when the removal or the 409 comes while the member was answering (`answeringAsks`), and a held Inbox answer is not sent (the store's per-provider closed set, `ui/ask-closed.ts`, read by the card's flush). The card names the other members ("Also for") or the room.

## Paged asks

Task 74e8fc07 (Nil, 2026-11-06: "Page is an ask"). Every page is a paged ask: the pager routes and the old pages moved to them, and the Pages tab is gone (internal-docs/pager-design.md, "Pages as asks").

- `page: true` (`page=1`) on the create gives the ask an alarm, `page: {state: "ringing" | "acked", ackedByUserId?, ackedAt?, delivery}`, fixed at create: an edit that sends `page` is a 400. It works with `member`, a member list and `room`; secret and sudo requests and reply drafts never have it (load check). Without a priority it is P1.
- `delivery` holds one pager send record (`PagerDelivery`) per recipient: the members the create resolved (`askMemberIds` at create; for a room ask, the room audience then). The set is fixed: a member who reaches the room later sees the card but gets no alarm. No wire carries `delivery`; the wires send `page` as `{state, ackedBy, ackedAt}`, `ackedBy` the member's current name.
- `POST /api/asks/:askId/ack` (`asks.ack`): whoever may answer the ask (`askVisibleTo`, or an owner through `askShownToOwnerAsOther`) acks it. The alarm stops for everyone and the ask stays open; a second ack is a 200 that changes nothing; a plain ask is 409 `not_paged`. The ack is an `acked` event in `ask_events`, with `byUserId`. Neither the ack nor a send record changes `updatedAt`.
- Cap: 50 open paged asks per source (`ASK_PAGES_MAX_OPEN_PER_SOURCE`), 429 `too_many_pages`: an app's by its registration, an agent's own without an app. The 500-ask cap is checked first.
- Delivery: the store's `onPage` seam tells `server/office-managers.ts` of each create, ack and close, which hands one page item per recipient (`server/page-items.ts`) to both pager channels. Each recipient gets the page on their own pager settings, linked to `/inbox/asks/<id>`, with the ask's first line as the title and the rest as the body, colour markup stripped (`shared/color-markup.ts`). A recipient who no longer sees the ask (`askVisibleTo`, read at each send) gets no further send. The close sends "resolved" from an in-memory snapshot, so a restart before that send loses it; an agent's removal closes its paged asks after the agent is gone, so the snapshot keeps the agent's name and room from the last item built.
- Rollback: an older server ignores `page` and loads a paged ask as a plain ask, with no alarm.

### Asks with no agent

Slice 2. The office's pages about a member's own feature (the WhatsApp and Discord supervisors, `officePagers` in `server/office-managers.ts`) open paged asks with no agent: `agentId: ""` (in memory, in `asks.json` and in the history; read it through `askAgentId`), `office: {feature, name}`, P1, for that member only, and `page.key` as the dedupe key. A raise with the key of the source's open paged ask (`openPaged`; a source is an agent, an app registration, or an office feature and member) re-raises it (`reraise`): new text is one `edited` event with `office` as the actor, the same text writes nothing, and it never re-rings. An app's page uses the same shape with `app` when the app has no live message target.

- Load check: an ask with `agentId: ""` has one member, a page and exactly one of `office` and `app`, and none of room, member list, options, link, affordances, step, secret, sudo or reply draft; `office` is never on an agent's ask. An older server loads it (its check wants a string `agentId`) and shows it to nobody, since no room has agent "".
- Audience: its member only (`askVisibleTo`, no room). Office owners see an app's ask with no agent as another member's; nobody else sees an office ask, also on `GET /api/asks/:askId` and the socket's removal push.
- Answers: reply, simplify, run and file-task are 409 `no_agent`; dismiss closes it with no message to anyone. The 500-ask cap is per agent and leaves these out; the 50 paged asks cap counts them per source.
- UI: the Asks tab lists them as runs under their source's name, placed by the sort like any ask (task dcb409d4; see the UI section), with only the priority filter; the card has Ack and Dismiss and no reply field.

## History

Task ff590b5e. Every closed ask is kept, as the logs are, in the `ask_history` table of `office.sqlite` (`server/ask-history.ts`): the entry as it was, its opening session included, and a closure `{at, outcome, byUserId?, answer?, taskId?}`. `ask_history_members(ask_id, user_id)` holds everyone the ask was for at the close and the closer, and `?member=` matches it as well as `member_user_id` (task 9461c464). The outcomes are `ASK_OUTCOMES` in `shared/types.ts`. `answer` is the member's words as the agent got them, so a tapped option is its text; a bare dismiss or filed task and every secret request outcome have none, and the record never holds a secret value. The table is not in `asks.json` because an older server's load check ignores unknown keys and would load a closed entry as open after a rollback; `user_version` stays 1, so an older server opens the database and ignores the table.

What happened before the close is in the `ask_events` table (task 62aa552f), one row per event, keyed by ask and agent. The kinds are `AskEvent` in `shared/types.ts`: `created` holds every editable field the ask had (`ASK_EDITABLE_KEYS`), and `edited` holds each field the edit changed with its value before the edit, null when the ask did not have it, plus `app` when an app edited (an agent can edit its app's ask, so `entry.app` does not tell who edited). An edit that changes nothing is no event. `simplify_requested` (task 30915188) holds `byUserId`, the member who asked, and `simplify_withdrawn` (task fc2021b7) the member who withdrew it; the history and log routes send it as `by`, the member's username, as they do the closure's. The close is the closure, and an app's withdraw has `app` there; the close is also a `closed` row in `ask_events` (`AskLogEvent`, task 302e7ea4), which `record` writes with the history row in one transaction, so a close is in both tables or in neither. A record's `events` leave the closed row out: they are what happened before the close. The store writes each other event after the `asks.json` commit and logs a failed write, as it does a close. An event's time is the entry's `createdAt` or `updatedAt`. With the created event, every edit's before-values and the closed entry, each version of the ask can be rebuilt.

The store's `remove(id, close)` takes the outcome (required, so a new caller does not compile without one) and `removeAgent` records `agent_removed`. The record is written after the `asks.json` commit, never before, so a failed save leaves the ask open and unrecorded; a failed record is logged and swallowed (the `recordAudit` posture: the agent already has the answer, and a throw would make a retry send it twice). A new ask takes no id the history holds in either table, so an id names one ask forever.

`GET /api/agents/:id/asks/:askId` returns the agent's own ask, open or else closed with `closed: {at, outcome, by, answer?, taskId?, app?}` and `events`, where `by` is the answering member's username at read time, null when there is none or the member is gone. `GET /api/agents/:id/asks/history` lists an agent's closed asks, newest close first, as `{asks, nextBefore}`; it takes `member=<username>`, `limit` (1 to 200, default 50) and `before=<nextBefore>`. Its reach is the logs' (`log:read` and `logSearchAccess`): every field of a closed ask is already in that agent's log, so the route shows nothing a log reader cannot read. A killed agent's owner reads it, so the handler needs no live agent. `GET /api/asks/:askId` (task 03f5c534) reads any agent's ask by its id, open or else closed, in the same wire as the agent's own read (one function serves both), with the same reach checked in the handler against the ask's agent; an unknown id and an ask out of reach get the same 404. The id is on the ask card, so a member can point another agent at an ask.

`GET /api/agents/:id/asks/events` (task 302e7ea4) is the agent's ask log: every `ask_events` row of the agent, open asks included, newest first, as `{events, nextBefore}`. Each item is the event's wire with `seq` and `askId`; a `closed` item has `by` as the closure has. It takes `askId=<id>` (a filter: another agent's or an unknown id is an empty page, not a 404), `limit` and `before` as the history, and has the history's reach. It is apart from the open-asks list (Nil, 2026-10-31): a reader follows the log by its `seq`.

Left out: asks closed before this change are not in the history, and asks opened before task 62aa552f lack some or all events; an open ask's read carries no events (its events are in the log); asks closed before task 302e7ea4 have no closed row in the log; there is no query across agents, so a Curator replaced by a new agent (a new id) starts an empty history (a handoff or clear keeps the id); no member UI; no retention cap. A closed ask's read file copies are no longer owed to the prune, so the record keeps their metadata only.

## Routes

The agent manages its own list on `/api/agents/:id/asks` (`self:affordance` and `agentParamMustEqualTokenAgent`, so a token reaches only its own `:id`; an entry of another agent is a 404 on its own path). Create and edit take the text/plain form (`shared/plain-text-form.ts`), or a JSON body whose prompt is `text` or its alias `prompt` (task 26e78c4c; both is a 400); on edit an absent or empty prompt keeps it (task 5ed624d3); create takes `member=<username>`, default the agent's manager, and the member must reach the agent's room.

Create and edit take an optional `link` to an office page (task 3ea6fdb3): one of `OFFICE_LINK_PATHS` in `shared/office-links.ts`, the canonical path of each UI page and `/integrations/<tab>` for each Integrations tab. The page and tab lists live there, and `ui/routes.ts` and the Integrations page read them, so a new page or tab is a target with no second list. The tab forms are also URL routes, accepted at load and rewritten to `/integrations` (task df206fe3); the agent form `/agents/<agentId>` is also accepted at load: it opens that chat and the address is rewritten to `/` (task 680747d8). The handlers check the link on write (422 `invalid_link`); the load check takes any non-empty string, so a target a later release drops cannot quarantine the file, and the card draws no link it does not know. On edit an absent `link` keeps it and `""` removes the key. A link can also be an outside page (task 0355f4b7): `outsideLinkFor` takes only a plain `https://` URL with no spaces or user name, and the card opens its parse, which keeps its path and query, in a new tab, named by its host. A secret request never has an ask `link`, since an older loader refuses one: its outside page is `secret.link`, which the open checks the same way.

A link can also name an agent's chat as `/agents/<agentId>` (task 9aaec0eb; `askLinkFor` parses both forms). On create and on an edit that sends it, the handler checks that the agent exists and that the ask's member can reach its room (422 `invalid_link`). An edit that does not send the link does not check it again, so an agent that later moves or goes keeps its link; the card then draws no button for an agent the UI does not have.

A link can also name one ask as `/inbox/asks/<askId>` (task 84aadfab; `askIdForSegment` in `shared/office-links.ts` is the one id check, for the link and for the address). The handler does not check that the ask exists. The same path is a URL route: accepted at load, it pins that ask above the Asks list and the address is rewritten to `/inbox/asks`. An ask id in chat text is a chip that pins the ask the same way (`ui/log-view/ask-refs.tsx`): an 8-hex id that is no task is looked up in the store's open asks, then once per page load with `asks.get`. A pinned ask the member answers is its AskCard, left out of the list; any other ask is drawn read-only (`ui/components/PinnedAsk.tsx`), a closed one with how it closed.

Create and edit take optional `options` (task ec730d2f): 1 to 10 answers the member can tap (one since task d05f2968, for a step the member does and then reports: the card starts the reply field with a lone option, so one tap sends it), each trimmed, non-empty, at most 80 characters, no two the same (`checkOptions` in `server/asks.ts`, 422 `invalid_options`). The text/plain form takes one `option=<text>` per option, a list parameter of `shared/plain-text-form.ts`. As with a link, the load check takes any non-empty list of non-empty strings, so a bound change cannot quarantine the file; on edit an absent `options` keeps them and `[]` (or a lone empty `option=`) removes the key. A secret request never has options.

An ask with options can mark one as the agent's recommendation (task d608a5be): `recommended`, the option's text, trimmed and checked against the options on write (`checkRecommended`, 422 `invalid_options`; the text/plain form takes `recommended=`). The mark goes with the options: on edit, sent options without `recommended` clear it, removing the options removes it, and `recommended` alone is checked against the kept options, with `""` removing it. The load check wants only a non-empty string on an entry with options, so a mark that names no option loads, and the card ignores it.

An ask can carry a `priority` (task 995fc76a), the board's `TaskPriority` (P0-P4), checked with `isValidPriority` on write and on load (422 `invalid_priority`; the text/plain form takes `priority=`). On edit an absent priority keeps it, and `null` or `""` (`priority=`) removes the key. Filing the ask as a task gives the task the same priority. The card shows it beside the age, in the board's colors (`ui/task-priority.ts`).

Create and edit take optional chat affordances (task dc79ace0): `commands`, `editFiles` and `readFiles`, at most `ASK_AFFORDANCES_MAX` (10) in total, counted on an edit with the lists it keeps. The text/plain form takes `command=`, `editFile=` and `readFile=`, list parameters like `option=`. Each item passes the chat route's own check (`server/affordance-checks.ts`, which `emitAgentTerminalCommand`, `emitAgentEditRequest` and `emitAgentReadFile` call too). The checks return a refusal kind, and the chat turns it into a system line while the ask routes turn it into 422 `invalid_command` / `invalid_edit_file` / `invalid_read_file`, or 403 `forbidden_path` for a credential store. A malformed list, an empty list on a create, or more than 10 is 422 `invalid_affordances`. Every item is checked before the read files are copied into the agent's files dir (`copyAskReadFile`, the copy the read-file chip uses), so a refusal makes and changes nothing; a copy failure after an earlier copy can leave an orphan, which a prune collects. A video or audio read file (by its media type) is not copied and has no size cap (task 37a660e8): the entry stores a reference, an attachment with a fresh `<uuid><ext>` filename and the absolute `path`, and `GET /api/asks/:askId/files/:filename` serves it to the ask's member with `agents.getFile`'s headers, probing the path again on each request (credential store, still a regular file). The agent that opened the ask reads a read file back, a copy or a reference, with `GET /api/agents/:id/asks/:askId/files/:filename` (task a5fb19fa): `agents.getAsk`'s rule, open or closed, and only a filename the ask lists. The prune does not owe a closed ask's copies, so that read can be a 404. The entry stores the resolved form: the command trimmed at the end, `{cwd, path}` per editor file, and the copy's attachment or the reference per read file. A filed task lists a reference by its path. An open ask's copies are owed like a queued message's attachments, so `queuedAttachmentsByAgent` in `server/office-storage-routes.ts` names them to the attachment prune. On edit an absent list keeps it and `[]` (or a lone empty value) removes the key. A secret request never has them.

The member answers on `/api/asks/:id/reply`, `/dismiss` and `/file-task` (`agent:converse` or `api:send-message`, `memberScope`). One function, `askVisibleTo` in `server/asks.ts`, decides who sees and answers an ask, from live state: the target member, or for an office secret request its named owner or else every office owner, and only while that member can reach the agent's room. `GET /api/asks`, the `ask_*` push, the answer routes and the secret request routes all call it. On the ask routes anyone it refuses gets the 404 of an unknown id; on a secret request's save and decline routes, 403 `forbidden`.

An office owner also reads and answers other members' open asks (task a49856f7; answers since task d555a32e). `askShownToOwnerAsOther` in `server/asks.ts` decides it: an owner, an ask `askVisibleTo` does not admit for them, not a secret request, whose agent is in a room they can reach. `GET /api/asks/others` lists those asks with the member's name (`askAgentWire`; 403 `forbidden` for anyone not an owner), so it never shares an id with `GET /api/asks`; the `others_ask_upserted` push follows the same rule, and `others_ask_removed` goes to every other owner on the close of an ask that is not a secret request. The answer routes (reply, dismiss, file a task, simplify and its undo) and `GET /api/asks/:askId/files/:filename` admit either rule: the owner answers under their own name, and the closed record names them.

The entry stores the agent's session when it opened the ask, for the reply note. No route or push sends it: `askMemberWire` in `server/asks.ts` drops it from the agent routes, `GET /api/asks` and `ask_upserted` (task 26dd1857).

## App asks

An app opens asks with its app token on `/api/app/asks` (task 1f453011): create, list, get, edit and delete, `app:ask` and `appScope`, the same body as the agent routes except `step` (400). An app has no chat, so the ask is in the name of the app's message target (`messageTargetAgentId`, else `createdByAgentId`): `agentId` is that agent, which gets the member's answer, and the entry adds `app: {name, createdAt}`, the registration shape secret requests use. Paths resolve against that agent's cwd, and the ask counts toward that agent's open asks. No target is 409 `no_target`, a gone one 404 `target_gone`, and an app record gone under a live token 404 `not_found` (the app message route's codes).

The ask goes to the app owner, or to `member` while the app acts for its live owner agent (`actsForAgent`; else 403, as `targetAgentId` on the message route); an app with no owner and no `member` is 409 `no_owner`. The member checks are the agent route's.

The app reaches the asks whose `app` matches its name and `createdAt`, wherever its target has moved since; an edit resolves paths for the agent that holds the ask. A deleted app's asks stay open on their agent, and a later app with the same name does not reach them. The target agent sees and manages them on its own routes. An app ask stores no `sessionId`: the agent did not ask it, so the reply note has no "opened in session" clause. The note, the dismiss and the filed task name the app (`askReplyNote`, `askTaskFields`), the `AskRef` carries `app: {name}`, and the card shows "From app <name>" above the prompt. An older server loads an app ask as a plain ask of its agent.

## The answer

A reply, a dismiss or a filed task goes through `agentManager.sendMessage`, the path a typed member message takes, with `opts.ask` (`sendMemberMessage` in `server/office-session-projection.ts` wraps it for the chat, API-token and ask sends). So it wakes or resumes the agent the same way and is refused only where a typed message is, with the same status and code. The ask closes once the message is accepted, which means its echo is durable or it is in the queue; a refused message leaves it open, and a failure after acceptance (a wake or backend error) closes it, as a typed message leaves the composer. Two differences from a typed message:

- It is never a slash command and never the answer to a pending prompt: it skips the typed-choice claim, and while the agent is busy or parked on a two-step prompt it waits in the queue. When the member's answer ends a prompt on an idle agent (/model, /effort, /resume, a cronjob choice), `sendMessage` flushes the queue, since no turn end does; a permission prompt ends inside a turn, whose end flushes it.
- The agent reads `[Member] [Reply to your ask <id>: "<whole prompt>"] <text>`; a dismiss says `Dismissed your ask` and the text is `Dismissed`, or the reason the member typed in the reply field (`text` on the dismiss route; a blank one is a bare dismiss). The `user_message` log entry carries `metadata.ask: {id, prompt, dismissed?, simplify?, taskId?, sessionId?, options?, recommended?}` (the whole prompt; the options and the recommended one when the ask had them, for the chat), and the queued item carries the same field, so the note survives a restart in the durable queue.

A filed task ("Not now; file as a task", task 2bb653b7) files a task in the agent's room before the message goes, so the message can name it: no priority, no assignee, the member as creator, the title from the prompt's first line and the description from `askTaskFields` in `server/asks.ts` (the prompt, the options, the link, the commands and files, the member's note, and the ask it came from). The agent reads `[Member] [Your ask <id> is now task <taskId>: "<whole prompt>"] Not now; filed as a task`, or the note the member typed in its place. A refused or failed message deletes the task and leaves the ask open, so a retry files one task. Reply, dismiss and file-task share one in-flight set, so a second answer of any kind gets 409 `ask_busy` and files nothing.

Simplify (task 30915188) is for an ask the member does not understand. `POST /api/asks/:id/simplify` (same auth as dismiss, no `text`: 400 `invalid_text`) sends `ASK_SIMPLIFY_TEXT` through the same path; the agent reads `[Member] [Simplify your ask <id>: "<whole prompt>"] <the fixed request>`, and `metadata.ask` carries `simplify: true`, which the chat shows as its translated label. The ask stays open. Once the message is accepted, the store's `requestSimplify` sets `simplifyRequestedAt` and records a `simplify_requested` event; a refused message leaves it unmarked, and a failed mark after acceptance is logged, as a failed close is. It shares the in-flight set, and a marked ask gets 409 `simplify_pending`. The agent's edit that changes the prompt clears the mark and sets `originalPrompt` to the prompt before the first rewrite; later rounds keep it. The edit routes never set either field. The card has Simplify last in the bottom row, after "Discuss in chat". While the mark is on, a banner that says the rewrite is coming takes the place of the options and the reply area (in both modes), with Undo; "Show original" joins the row under the prompt once `originalPrompt` is set. Not on a secret request (409 `secret_request`).

Undo (task fc2021b7) is `POST /api/asks/:id/simplify/undo`, with the same checks as simplify; an ask without the mark gets 409 `simplify_not_pending` and nothing is sent. It sends `ASK_SIMPLIFY_UNDO_TEXT` with `metadata.ask.simplifyUndone: true`; the agent reads `[Member] [Simplify request withdrawn for your ask <id>: "<whole prompt>"] <the fixed words>`. Once the message is accepted, the store's `cancelSimplify` clears the mark and records `simplify_withdrawn`. When the agent's rewrite cleared the mark while the message was on its way, it writes nothing and the route still answers 204: the agent has the message, and the rewrite stands. The server still accepts an answer while the mark is on; only the card holds it back.

## Step asks

A step ask (`server/step-asks.ts`, task c71cb60f) is a plain ask with `step`: a step on the Integrations page that is not a typed value (a provider sign-in, an MCP OAuth sign-in, a browser pairing, a room's GitHub link). The agent sends `step` on the ask create, without `link`; `check` refuses a step that is malformed, that the member may not do, or that is done (409 `step_done`), completes it (the manager as an MCP server's owner, the agent's room for a GitHub link) and gives the link to the step's tab. The step and link are fixed: the edit refuses both. The member can still reply, dismiss or file it.

An action step (task e3d1bc63; `ActionStepRequest` in shared/types.ts: `agent-access`, `member-room`, `member-role`, and the settings kinds below; the types are in shared/action-steps.ts) is a human-only action the member runs from the card. It has no link: `routeOf` gives the office route it runs, and the card's Apply posts `POST /api/asks/:askId/action` (asks.runAction). Only the member the ask is for runs it (else 404), one run per ask at a time (409 `action_in_flight`). The handler dispatches the route in process through the executor with the caller's own identity (`via: "ask"`), so that route's guards, preconditions, events and audit row apply, and the row names the ask. The answer is the route's own. The run does not close the ask: the change does, through `reconcile` (for `agent-access`, every access change in the agent manager calls it, so a change by hand closes it too). At create, `check` refuses a target the asking agent cannot reach exactly as a missing one (422 `unknown_agent`), before every other check; then a member who fails the route's own authorization (403 `member_not_allowed`, verdict only), and a stop the slider refuses past its guards (the engine, the folder rule; 422 with its code).

The member kinds name the member by username and store the id. `routeOf` builds their route when it runs, from the member as they are then: the name for the path, and for `member-room` the live room list plus or minus the one room, sent whole to `PUT /api/users/:username/access` (no pack). A member gone since the create is 422 `unknown_member` at the run, a member made an owner since then 422 `owner_has_all_rooms` (a grant closes as done first: an owner has every room), and a grant of a room closed since then 422 `unknown_room`; a removal on a closed room is done, as the close takes the room from every member. Members are not hidden from agents (the member list is public), so `unknown_member` means only that none exists; the room is the limit, answered as a missing one when the asking agent cannot reach it. `member-room` also refuses the lobby and an owner (every member reaches the lobby, an owner every room). `member-role` needs an office owner explicitly (users.update lets a member edit their own record and refuses the role in the handler) and refuses a demote of the last owner (409 `last_owner`); the session lockout check (`would_strand_office`) stays with the run. The users.ts access hook (every persisted role or room change) calls `reconcile`. The card marks a change that widens the asking agent's manager (a room granted, a promote) and a demote of the member the ask is for. Later kinds (removal, update, storage) join the same table.

The settings kinds (part 3) cover each settings route no agent token reaches: `member-pack` (the pack on `PUT /api/users/:username/access`, the live rooms sent with it), `member-preferences` and `member-view` (the member's own `PATCH /api/me/preferences` and `PUT /api/me/view/*`), `office-settings` (`PUT /api/office/settings` with the live version) and `backup-settings` (`PUT /api/backup/settings`). A route a privileged agent reaches has no kind: the `agent-access` ask for Privileged covers it; office settings have one, as the privileged flag gives much more than one switch. A `set` is checked with the route's own parsers (`parsePreferenceChange`, `officeSettingsFieldError`, `backupSettingsShapeError`), and the stored value is the parsed one, so the done predicate compares like with like (a preference with no value compares as its default). A `member-preferences` step may not set `recordingWords`: the card would show the private word list. `member-preferences` and `member-view` go only to the asking agent's manager: the fields are private, and `step_done` at create would tell an agent one bit of another member's record. `member-view` refuses sound or push for a hidden or tucked room (409 `room_hidden`, `room_tucked`) at create and at the run, since the view core drops those without an error; the card says when the change also stops the room's alerts or turns its sound on. A backup create touches no disk (the save creates the folder), and refuses a folder change while `ISOMUX_BACKUP_DIR` is set. The preferences, view, office settings and backup save paths call `reconcile` after a write.

The credential kinds (part 4): `sign-in-link`, `member-sessions` (sign out on every device), `session-revoke` (one session, task 43b67f3a), `sign-in-links-revoke`, `api-token`, `api-token-revoke` and `office-access`. `routeOf` gives a list of routes; `runAction` runs them in order to the end of the list, also when the change closes the ask on the way, stops at the first refusal and answers with the last route's answer, so a retry after a partial run does the rest. A sign-out revokes every session live at Apply, the applying session last; a links revoke takes every pending link. The done predicates read the ask's age (`isDone` gets `entry.createdAt`, null at the create): a link or token made since the ask opened (by the card or by hand) closes `sign-in-link` and `api-token`; none of the sessions or links live when the ask opened closes `member-sessions` and `sign-in-links-revoke`, so a later sign-in does not hold it open. The split is by the millisecond, so the create waits past the newest of those links, sessions or tokens before the ask is stored: none from before shares the ask's `createdAt`. A stamp more than 5 ms ahead of the clock (a clock set back) skips the wait, so the create cannot hang. `member-sessions` and `sign-in-links-revoke` check owner-or-self at create (the routes' preconditions, which `authorizeRoute` does not run), and a sign-out refuses 409 `would_strand_office` at create when it would end the last owner sessions; the auth mutex checks again at the run. `api-token` is checked with the mint's own parser (`parseApiTokenCreate`, with the same limitable rooms). `session-revoke` stores the member's id and the prefix; the create refuses 422 `unknown_session` alike for a prefix of another member's session, a gone one and one that never was, checks owner-or-self as a sign-out, and refuses 409 `would_strand_office` when that one session is the last owner session (`wouldRevokeMemberSessionStrandOffice`, by member and prefix); the route checks again in the auth mutex at the run. It is done when the member has no live session with that prefix. Agents name the session from `GET /api/users/:username/sessions` (`sessions.listForMember`: agents only, their manager or any member with an office owner's reach, office read area; prefix, device, user agent, created and last seen). `api-token-revoke` stores the token's owner (`userId`) for the card, and answers 422 `unknown_token` alike for a token that is gone and one the member may not revoke. `office-access` stores the address normalised as the save stores it, and refuses 403 `hosted_access_managed` on a Hosted office (`hostedAccessRule`, the save's own rule). The invites list emit, the sessions-changed hook, the token mint and revoke and the access save call `reconcile`. A sign-in link or token is only in the run's answer to the member's page: the card puts it in the store's `askResults` (memory only), and the Inbox and the chat's ask stack draw it (`AskResultCard`, in the shared `MintedSecretBox`; another member's link says to send it, the member's own to open it) until Close, since the ask closes as it is made and `ask_removed` can come before the answer. `asks.runAction` is user-scope, so no agent or API token runs one.

The office kinds (part 5): `member-remove`, `member-restore`, `member-purge`, `office-update`, `storage-prune` and `storage-compress`. A removal stores the live member's id and runs `DELETE /api/users/<name now>`; a restore or a delete for good resolves the username against Removed members (a removed member's name stays reserved) and runs by id, and a member restored or deleted since the create is 422 `unknown_member` at the run. A removal is done when no live member has the id, a restore when one does, a delete for good when the id is neither live nor removed (so the 30 days running out closes it too, with a line that says not who deleted them). A removal refuses 403 `owner_self_delete` and 409 `would_strand_office` at create, as the route's preconditions do. `office-update` takes no tag: the create stores the latest release the update checker knows, and refuses 409 `not_managed` unless the status is release mode applied by the host, 409 `no_release` with no known release; it is done when the running release is that one or later (`compareCalver`), which the boot's reconcile reads after the restart. `storage-prune` is parsed with the route's own `parsePruneRequest` as an apply (`keepPerAgent` required for transcripts) and `storage-compress` with the same age floor. At the create both refuse 409 `step_done` when a dry plan finds nothing; an open one is done when a prune of the same target (or a compress) applied since the ask opened covers it: an age line at or under the step's and at most as many kept per agent. `createStorageOps` keeps the last apply per target in memory, set only after an apply returns without an abort, and calls `reconcile` right after it, so the stamp only has to live from the apply to that reconcile; reconcile walks no disk. The removed-members emits of the users routes, the minute sweep's expiry and each prune or compress apply call `reconcile`. The card has no Undo, so it asks again before a destructive Apply (Nil's UI rule in AGENTS.md, 2026-11-05): a removal, a delete for good, a prune after its dry-run preview, an update, and the part 2 and part 4 kinds that take something away (a room access removed, an owner made a member, a sign-out, a links or token revoke). The update card shows a started state after the 202 and offers no second Apply. A prune or compress answer goes to `askResults` as the page's result line.

One predicate per kind reads the current state (a connected account for the member and scope, a signed-in OAuth server, a paired browser, a linked room). The create uses it, and `reconcile` closes every open step ask whose predicate holds, settling each once (the ask's removal decides) with a system line and an office notice (`emitAgentStepAskDone`, metadata `stepAskDone`). The hooks call `reconcile` and say only that something changed: every `provider_accounts_updated` emit, the MCP OAuth callback, a browser pairing, a saved GitHub link, and the boot after the agents are restored. A predicate that throws leaves its ask open. The load check takes any non-empty step kind, so a later release's step loads and never closes itself here.

The card draws the step's own control (`ui/log-view/AskStepBlock.tsx`, part 6) in place of the link, which stays on the entry for older clients: the provider sign-in card at the step's scope, the MCP server's Sign in, the browser pairing pane and the room's GitHub link form, each the Integrations page's own. A control acts as the viewer, so a personal provider sign-in or a browser pairing on another member's ask draws only who does it. An MCP sign-in from the card sends `{askId}` to the sign-in route (an ask id's shape, else 400); the pending flow keeps it, and the callback sends the member who started the flow back to `/inbox/asks/<askId>?mcpSignIn=<code>` (another member's browser, or an unknown state, goes to `/integrations` with no id). App reads the code once at boot and gives it to that ask's card, which shows a failure with Sign in again; an ok lands on the ask, closed by the reconcile.

## Secret requests

A secret request (`server/secret-requests.ts`, `POST /api/agents/:id/secret-requests`) is an ask with `secret: {requestId, scope, name, hosts, form, reason, app?, ownerUserId?, answerUserId?}`; the prompt is the reason. The ask is the only record of an open request, so it survives a restart. It never holds the value: the save body goes to the secret store only.

- A personal request is for the member in `memberUserId`: the agent's manager when it opened, or the member the agent named (task 315a62c0). It saves into the secrets of `ownerUserId` (the manager, or the app's owner for an app request; a request from before the field saves into `memberUserId`'s). An office request has no `memberUserId` and is for the owner in `answerUserId`, or every office owner when it names none, while they can reach the room; the first save or decline closes it for all. The named owner is not in `memberUserId` because an older server's load check refuses an office request with a member and would quarantine the whole file after a rollback. The answerer must be allowed to write the target secrets (that member, or an office owner): checked at open (403 `member_not_allowed`) and live in `askVisibleTo`.
- A request can be for a variable or an MCP server instead (`kind: "variable" | "mcp-server"`, task c71cb60f). The type is a union on `kind` (`shared/types.ts`); a secret has no `kind` on disk. The new kinds stay in `AskEntry.secret` and keep `hosts: []` and `form: {kind: "authorization"}` on disk, so an older server loads them as secret requests after a rollback: a masked form that saves into the wrong store, never a reply box that would put a value in the chat. Every rule here that keys on `secret` covers them. The load check takes any other non-empty `kind`, as it takes any link, so a kind from a later release cannot quarantine the file after a rollback: such a request's save is 409 `request_unsupported` (the ask stays), its card offers Decline alone, and a decline or the agent's delete closes it (`knownValueRequest` in `shared/types.ts`). A variable request saves `{value}` through `writeVariable`, an MCP server request `{url, secret, oauth?}` through `writeMcpServer` (`server/connection-writes.ts`), the same functions the Integrations routes call, so the after-effects match. The open refuses a variable or server that exists in the target scope (409 `variable_exists`, `mcp_server_exists`), and so does the save. An MCP server request's `url` and sign-in (`secret`, or `oauth: true` for an OAuth server, never both) are proposals; the open checks that a proposed secret exists in the target scope, not its host, since the member can change the URL. An OAuth save makes the server with dynamic client registration, and the card then starts the sign-in without waiting on its own mount (the save closed the ask); if the start fails, the Integrations row offers the sign-in. An older server loads an `oauth` request and saves a plain server. No line, answer or log holds a value or a URL.
- A request can also be for a Discord bot (`kind: "discord-bot"`, task c92d60f4), with the fixed name "Discord bot" and the same on-disk fields. It is personal to the agent's manager, takes `reason` and an optional `applicationId` (task f242899f: the application the agent made in the member's browser; the card then links its Bot page and its invite, and the open refuses anything but 17 to 20 digits), and only the manager answers it (no `member`, no office owner); the open route refuses an agent without `integration:manage`, because only a privileged agent can then route the bot. The save `{value}` calls the Discord supervisor's connect instead of a store write. The connect awaits Discord, so the request is busy until it ends: a second save or a decline in that time is 409 `request_busy`. A refused connect answers its code and keeps the ask; a connect that throws answers `check_failed`. If the agent withdrew the ask during the connect, the bot stays connected and the agent still gets the settled line. A release that knows value kinds but not `discord-bot` offers only the decline.
- An app request (`app: {name, createdAt}`) has no hosts. Its save re-checks that the app is the same registration and, for a personal request, still the owner's (409 `app_gone`, the ask stays), and gives the secret that app's grant.
- The member answers on the secret request's save and decline routes. A reply, dismiss or filed task gets 409 `secret_request`, so a value typed there never reaches the chat or the agent. The agent's edit gets the same 409; its delete withdraws the request.
- The save creates the secret, then removes the ask, with no await between the permission check and the removal. If the removal fails, the agent is still told, since the secret exists. A decline removes the ask first and tells the agent only after that.
- The chat shows the agent's call and a system line with the outcome. The agent gets the same line, in English, as an office notice (`QueuedMessage.notice`): its sender is the member who answered, so the turn and the usage cap are that member's, but the agent reads only `[Isomux: <line>]`, and its delivery writes no chat entry. The queue strip leaves notices out. A `secret-request` log entry from a server before this change draws a read-only card: its outcome, else closed.

On the Inbox the button opens the chat panel on the agent instead, and the panel's composer takes the focus request the same way and spends it.
- In the agent's chat, an answer shows a one-line "Ask" link (`ui/log-view/ask-link.tsx`). A click on "Ask" scrolls to the "Create ask" card whose result holds the id; without that card the label is text. When the line cuts the prompt, or the prompt has more lines or options, a click on the prompt shows it whole with its options under the line, and a second click folds it.
