# Design: a member's agents on their own OS user

Board task b94dfd25. Status: design, 2026-11-14, waiting for Nil. Reviewed by Isomux Reviewer 3 (round 1: five holes closed in this version). It replaces the direction of task 01f5038c (the server moves to its own OS user, [os-user-split-design.md](os-user-split-design.md)) and reuses its runner, its `AgentHost` seam and its inventory of spawn sites (that document, sections 1-4).

## 0. Summary

- **Default: no change.** The server, its state and every agent run as the office's OS user, as today. Nothing migrates on an office that does not use the feature.
- **Opt-in, per member.** An owner turns on "Own OS user" for one member who is not an owner (an owner sets office variables and manages other members, so no OS user can fence an owner). The member's agents, terminals, apps and schedules then run as a new OS user, for example `isomux-alice`. All agents of one member share that user. No per-agent users (Nil, 2026-11-14).
- **What it gives.** The member's agents cannot read the office user's home (with `~/.isomux`: tokens, secrets, other members' sign-ins and variables) or the processes of other members, and cannot act as another agent. The member cannot use an agent that runs as the office user as a shell (section 3.1).
- **What it does not give.** The office user, and every agent that still runs as the office user, can read the isolated member's files and act as their user. Nil accepted this: the owner chooses which members to isolate. Messages to other agents stay a soft boundary.
- **Root, only for the account.** Turning it on or off needs one root command. Root makes or locks the user, its home, the share and a system unit that runs the member's runner. Root never walks or changes owner of a file tree: the member's files move through the runner. No root process stays running, and no pool of users is made in advance.
- **Collaboration.** Messages, asks, tasks, memory and history go through the office API with each agent's token, so agent-to-agent work does not change. Folders are shared with POSIX ACLs, which need no root; write sharing with an office-user agent removes the isolation (section 3.2).

## 1. Mechanism

### 1.1 One runner per isolated member

The agent runner of the split design (server/agent-runner/, on main, switched off) runs as the member's user, one process per isolated member. The server connects to it and asks it to start processes and do file work as that user. The direction is the reverse of the split: there, the server user was the trusted one and moved out; here, the server stays and the less trusted member moves out.

- **Code.** The runner, its fixed entries and the terminal sidecar are one `bun build` bundle. The server builds it at the first connect of a member runner, once per server process; an office with no isolated member never builds it. The bundle, a copy of `bun` and the engine packages that the office uses (Claude, Codex, OpenCode, same versions) live in the member share, in `runtime/<hash>/`, and `runtime/current` is a symlink to the one in use. The server writes them as the office user: a hard link of its own file when the share is on the same file system and the source is safe to link, else a copy. The member cannot change the code that its runner runs.
  - The hash covers the bundle bytes, the `bun` bytes and a list of (path, size, mode, mtime) of each engine file, so a changed byte gives a new hash. A copy keeps the source mtime.
  - At connect, the server installs the runtime before it reaches the runner (a share whose runtime is broken has no runner to answer), then compares the hash that the runner reports with the installed one. On a difference it sends the runner `exit`, and the unit (`Restart=always`) starts the new bundle; that cuts the member's turns, as an office restart does. From the install to the reconnect, the member's host is not ready. One round per connect attempt: a second difference leaves the host not ready, and the attempts back off. A `runtime/<hash>` that exists and passes the share check is not written again, so a runner that lies about its hash costs at most one install.
  - The server removes an old hash only after the reconnected runner reports the new one, and never the hash that a connected runner reports.
  - A source with a setuid or setgid bit, or with group or other write, is copied with mode 0755 or 0644, never linked: a hard link shares the inode and its mode, so a linked writable file would give the member write on code that the office runs. A symlink in an engine package fails the install; it is not followed.
  - **Share check**, at each connect (before the install only the parent and the share itself, so that the install can repair a broken runtime; after it, all of it): the share's parent is owned by root, has no group or other write and is not a link; the share has the member's group and no other bits; every entry in it is owned by the office user or root, has no group or other write (with an ACL, the group bits are the mask, which caps every named entry) and no setuid or setgid bit on a file; it holds only regular files, folders and one symlink, `runtime/current`, whose target is the 64-hex name of a folder in `runtime/`.
  - The runtime is the office user's, so no engine updater that runs as the member can change it; that is why Codex needs no variable. The member host's env also sets `DISABLE_AUTOUPDATER=1` (Claude) and `OPENCODE_DISABLE_AUTOUPDATE=1` (OpenCode), so they do not try. The member user needs no read on the code tree or on anything in the office user's home.
  - The bundle has four parts, picked by its first argument: `runner`, `entry <name>`, `pty` (the terminal sidecar) and `opencode-helper` (the OpenCode server helper). The runner reports the name of the runtime folder that it runs from as its hash.
- **Unit.** A system unit template, `isomux-member-runner@<osuser>.service`, `User=%i`, `RuntimeDirectory=isomux-runner-%i`, mode 0711, running `/var/lib/isomux-share/%i/runtime/current/bun` (the path written with `%i`, not from a variable). `RestartSec=5` and `StartLimitIntervalSec=0`, so a unit whose runtime is broken comes back when the server repairs it. In the container (no systemd), the entrypoint starts one runner per recorded member user while it is root.
- **Socket.** `runner.sock` in that directory, mode 0666. The runner accepts only the office uid (`SO_PEERCRED`), so the member's agents cannot drive it. Every process of the office user can connect. That is the accepted reverse direction.
- **Rule: every runner reply is member data.** The member owns the socket's directory, so any member process can replace the socket with its own listener. The server therefore treats a pid, path, home, env or file that a runner sends as data of that member: it never signals a runner-sent pid as the office user (a kill goes through the runner), never opens a runner-sent path itself, bounds every size and every wait, and sends a runner only what that member's agents may have. Slice 1 checks the 18 `process.kill` sites of the server for pids that come from a runner.
- **Server side.** `getAgentHost()` is renamed `officeAgentHost()`, and `hostFor(userId)` (server/member-hosts.ts) picks the host: the office host for a member without an OS user (and for agents without a manager), the member's `RunnerAgentHost` otherwise, and a host that fails every operation while that runner is not connected. The record of OS users is `STATE_ROOT/member-os-users.json` (server/member-os-users.ts), not users.json, so a removed member or a users.json that does not parse never moves an isolated member to the office user. An env built for an isolated member carries the member's tag: the member's host refuses any other env, and an office host refuses a tagged one. Most of the 32 call sites build an env per manager, so the manager's id is at hand; slice 1 lists the rest. The base env (HOME, USER, PATH, `XDG_RUNTIME_DIR=/run/user/<uid>`) comes from the runner, never from the server's `process.env`.
- **When the runner is down.** The member's agents do not start; the turn fails with "the member's OS user is not ready" and the Members page shows the state. The server never falls back to the office user for an isolated member.

### 1.2 Trusted checks, per member

The split design's trusted checks (section 2.4 there; server/split/trusted-checks.ts) run for each isolated member when the server connects to its runner, and the root command runs them before it reports success. For the member user:

- its uid is not 0 and not the office uid;
- it is not in any group of the office user, nor in `sudo`, `wheel`, `admin`, `adm` or `docker`;
- it has no effective search on the office user's home, and no effective write on `STATE_ROOT`, the code tree or their ancestors (mode bits and ACLs; on a self-hosted box whose home is `o+x`, the command refuses and names the `chmod`);
- it cannot become root (the installer's hardening gate, for that user).

A failed check stops that member's agents, not the office. The runner diagnostic (denied reads tried by the runner) is logged and is never the proof.

### 1.3 Files

| Area | Where | Owner | Holds |
|---|---|---|---|
| Office state | `STATE_ROOT`, unchanged | office user, 0700 | as today |
| Member agent space | `<member home>/.isomux-agent/` | member user | the member's `provider-homes/<userId>/`, OpenCode profiles, the codex-home of their sessions, and the data, units and env files of their apps |
| Member share | `/var/lib/isomux-share/<osuser>/` | office user, group = the member user's group, 2750 | what the server writes and the member's agents only read or run: the runtime (runner bundle, `bun`, engine packages), their uploads and shown files, the Codex safety hook, the CA bundle of the secret proxy, the OpenCode authority socket |

- The share is outside the office user's home and uses the member user's own group, so one member cannot read another member's share. Root makes it once; after that the server writes into it with no root.
- Docker: member homes and shares live on the data volume, because the image keeps neither `/home` nor `/var/lib`. The office user owns `/var/data`, so the entrypoint makes one root-owned parent, `/var/data/members` (0755), and refuses to go on when it is a link or not owned by root. Homes and shares go under it. The entrypoint recreates the member users from `/var/data/members/users.json`, which the enable command writes as root. It reads the file only when the folder and the file are not links, are owned by root and have no group or other write, checked on the open file; a bad file skips every member. It skips an entry whose uid is 0 or the office user's, is outside `UID_MIN`..`UID_MAX`, is not unique, or whose name does not match the command's pattern or has another uid in `passwd`. It never changes the owner of a home: a home that the recorded uid does not own skips that member. The layout is `home/<osuser>`, `share/<osuser>` and `etc/` (the `.made` marks) under `/var/data/members`, each parent root-owned with no group or other write; a bad parent skips every member, and the office starts either way. Since the office user can rename what is under `/var/data`, every change there goes through `deploy/container/member-users.py`, on file descriptors of those folders. disable without `--delete-user` keeps the entry with `"locked": true` (recreated locked, no runner), and enable picks a uid and gid above every recorded one, so a uid that owns files on the volume never goes to another member. In place of the unit, each member's runner runs in `deploy/container/member-runner-loop.sh`, started as the member with a fixed environment, no_new_privs, no inherited fd and its own session; `$HOME/.tmp` stands in for PrivateTmp.
- Workspaces stay where they are. New agents of an isolated member start in the member's home. Section 3.3 covers the agents whose folder the new user cannot reach.

### 1.4 What an office-user process opens, starts in or runs

An office-user process must never run code that an isolated member can write, and never read a path for them. Two parts:

**Paths that an isolated agent names go through its host** (the fence of the split design, section 4 there, per member):

- read-file, the editor (open, save, watch), the app thumbnail `{path}`, browser upload, Codex image views, skills in the cwd and in the engine home, the file tools that Isomux serves to agents at Folder and Web, and cwd checks;
- the `/isomux-diff` and the diff route, whole: git runs `.git/config` hooks (`core.fsmonitor`), so a diff that the server runs in an isolated agent's repo runs that agent's code as the office user;
- transcript reads and the session store (Claude fork and history), the Codex rollout walk and the OpenCode database check (the parked slice 4 of task 01f5038c);
- ask commands that a member runs, account and usage probes, and preview capture.

**An isolated member does not steer an office-user agent** (section 3.1). The folder of an agent is where its engine loads project settings, hooks, MCP config and git config, with no model in the loop.

### 1.5 Secrets and variables

- Office variables and the member's own variables reach the isolated agents as today. Other members' variables and every secret value stay in `STATE_ROOT` and in other users' processes, which the member user cannot read.
- The secret proxy serves a client that gives the proxy password, so isolated agents keep using their secrets (`HTTPS_PROXY` carries it). Placeholders are per scope and random, so a placeholder of another member is unknown to them. The CA bundle is copied into the member share.
- Headless Chrome drops the password, and the proxy's same-uid exception does not cover the member user, so a preview of a page on a secret's host gets 407. Noted, not fixed.

### 1.6 Sign-ins and the office fallback

- The member's own Claude, Codex and OpenCode sign-ins move to their agent space.
- **Claude fallback.** Today the fallback points `CLAUDE_CONFIG_DIR` at the office account's directory, so the conversation runs next to every office agent's transcripts. An isolated agent must not get that. In its place, an isolated member's agents keep their own `CLAUDE_CONFIG_DIR` and get the office credential as `CLAUDE_CODE_OAUTH_TOKEN`: a long-lived inference token that the owner makes once (`claude setup-token`, an Integrations step shown when the first isolated member has the fallback on). It only runs inference and is easy to revoke, unlike the office refresh token. It expires after one year: Integrations shows the date, and the office pages the owner before it. Slice 4 proves that the env token wins over a sign-in in the member's own config dir. Nil, 2026-11-14: that the isolated agents can read this token is a documented limit that the owner accepts with the setting.
- **Codex fallback: off for isolated members.** Codex keeps a refresh token in `auth.json`, and a refresh rotates it. A copy that the member's Codex refreshes signs the office out; a shared file that the member can write lets the member put in their own account, and then every office Codex agent sends its turns to that account. The Members page says why the setting is off.
- **OpenCode** reads its sign-in from the member's profile, which moves with the member.
- Usage readings run as the user that owns each sign-in, so they keep working.

## 2. Turning it on and off

### 2.1 What the owner sees

Settings → Members → a member → **Own OS user**. Off by default. Turning it on shows one command and what it does, in two lines. Where the office's user has sudo, a button puts the command in a terminal panel, where the owner types the sudo password. The section then shows "waiting for the command", and after it, "on: runs as `isomux-alice`", or the failed check.

The command never runs a file that the office's user can write (an agent could change it before the owner runs it as root):

- installer and Hosted: `/usr/local/sbin/isomux-member-user`, installed root-owned by the installer and the updater;
- container: the same file in the image, run with `docker exec -u 0`;
- self-hosted from a checkout: the script at the office's release tag, fetched from GitHub over HTTPS and piped to `sudo bash`.

Until the last slice ships, the server answers "not ready" on `admin.sock` and the command stops before it changes anything.

### 2.2 `isomux-member-user enable <member> [--user <osuser>]`

Root acts only on the account and on new, empty places it makes:

1. Ask the server about the member over `admin.sock` (it answers uid 0 only).
2. Create the user (default `isomux-<member slug>`, a home, no password, no extra groups) and make the share. Refuse an owner, and refuse a user that exists: the command deletes only a user that it made (it keeps a root-owned mark), so `disable --delete-user` never removes a person's login.
3. Ask the server over `admin.sock` to install the runtime in the share (1.1); root writes no code. Enable the user's linger, so its apps run without a login, write the runner unit's env file, and start the unit.
4. Run the trusted checks. Tell the server to go on (`admin.sock`). The server records the OS user and tries to connect for up to 30 seconds (the unit may not listen yet); when it cannot, it removes the record and the command undoes its steps.

The server then does the rest with no root (`server/member-user-admin.ts`, `server/member-move.ts`):

1. It holds the member's agents. A running turn is cut, every process of their agents (and its background work) and their OpenCode servers end, and new messages queue. An agent spawned for the member during the move is not held: its first start fails as not ready. A second go-on for the member is refused while one runs.
2. It plans the move from the office's paths: their `provider-homes/<userId>/`, their two OpenCode profiles, the Codex rollouts of their agents' sessions (by thread id, in the office Codex homes), and the Claude transcripts of their sessions (the exact `<id>.jsonl` and `<id>/` under each root searched before, with no folder scan).
3. It records the OS user and marks the member as moving. Until the move ends, their host has its paths but starts nothing: a schedule run that fires during a move fails as not ready. Then it connects, as above.
4. It streams the planned files to the runner (the `files-in` entry), which stages them in `<agent space>/.move-in/<nonce>/` as the member. Before it writes a byte, the runner refuses when its file system has less free space than the planned total plus a margin. `files-place` then links each one to its place and never replaces a file. A file there with the same bytes counts as placed (a rerun).
5. After the runner confirms every file, the server rewrites the Claude pins of the moved sessions to the member's roots. Codex has no pin: a member's turns read their own `CODEX_HOME`.
6. It ends the move (`files-done`), releases the queues, which then flush on the member's host, and deletes its own copies of what moved: each file that moved, when an `lstat` through real folders still shows the inode that the walk read, then the folders that are now empty. A file that the move skipped stays in the office.

A failure before step 6 undoes the runner's side (`files-undo` removes only what `files-place` placed, as the member), removes a record that this call made, and releases the agents. The office copy stays. A file with a destination outside the member's home (their own `CODEX_HOME` elsewhere) is skipped and logged.

The command waits up to 3 hours for go-on and disable, more than the server's longest move (`deploy/isomux-member-user.sh`, `MOVE_VERB_LIMIT_S`).

If the server stops during a move, the record stays and the office copy stays. The member's agents then resume without the moved conversations, and each connect logs that an earlier move did not finish while the office holds a file that a move would take. A rerun of enable finishes it. For a member who already has their own OS user, the plan reads only the office's roots, never a path in their home.

### 2.3 `isomux-member-user disable <member> [--delete-user] [--keep-files]`

1. The server moves the member's agent files back (`server/member-move-out.ts`). It refuses when another go-on or disable for the member runs, and when their runner is not connected (then the owner starts it, or runs `disable --keep-files`, which leaves the files in the member's home and only stops using their host):
   1. It holds the member's agents as on enable and marks them as moving: no member process starts while their files are read.
   2. It asks the runner for their provider homes, their two OpenCode profiles, the Codex rollouts of their sessions (by thread id) and the Claude transcripts and `<id>/` folders of their sessions. The runner reads them as the member (`files-out`) with the same walk rules, and streams records that name the requested source and a path under it.
   3. The office trusts only the bytes. Each record must name a requested source. A Codex record must be the rollout of the thread it asked for, and a Claude record must be that session's transcript or a file under its folder. Only the member's own trees take any normalised path. The office picks every destination: `STATE_ROOT/provider-homes/<userId>/`, its own OpenCode profiles, the office Codex home, the office Claude root. It refuses the whole stream on any other record, and on a breach of the size bounds or of the free space of each destination's file system.
   4. It writes each file `O_EXCL|O_NOFOLLOW` 0600 into `.member-move-out/<userId>/<nonce>/` at the top of `STATE_ROOT`, `AGENT_ROOT` or its Claude root, whichever is on the destination's file system. It then links the file into place without replacing a file: a file there with the same bytes counts as placed.
   5. It rewrites the pins of the transcripts that arrived in full. A requested source that sent nothing is logged.
   6. The runner removes the member's copies of what it sent (`files-remove`, only a file whose inode did not change) and names what it kept. The office logs each kept path. A later enable then fails on that path until root deletes it.
   7. The office forgets the OS user and releases the agents, which run as the office user.
   A failure before the pins undoes the office's side. The record and the member's copy stay, and the command stops before it changes the OS user. If the server stops during a disable, the record stays and so does the member's copy (`files-remove` may have run part way). The placed office files and rewritten pins may stay as well: the member's pin rule ignores office roots, so their agents resume from their own copy. A rerun of disable takes the identical files. If a member turn changed a file in between, the rerun fails and names the path, and root deletes it.
2. Root stops the runner unit, ends every process of the user (`loginctl terminate-user`), disables its linger, removes its crontab and `at` jobs, removes the share and locks the account.
3. The server runs the member's agents as the office user again.

The OS user and its home stay, locked, unless `--delete-user`. Files the member's agents made outside their agent space keep their owner.

A removed member: the office deletes their agent files through the runner (logged when the runner is not connected), and the list of removed members shows the `disable --delete-user` command until the OS user is gone.

### 2.4 A change of manager

A manager change between hosts is refused: the agent and the new manager's agents must run as the same OS user. The host of a member with a record in `member-os-users.json` (ready, not ready or malformed) is their own; every other member's is the office user. So office user to member, member to office user and member to member are refused; office member to office member and a member's own agents are not. The check (`sameAgentHost`, server/member-os-users.ts) runs in every path that changes an agent's manager:

- `PUT /api/agents/:id/manager` answers 409 `member_os_user` and changes nothing: the check comes before the ceiling clamp, the fields, the token and the session stamps. The owner spawns a new agent for the member instead.
- The restore of a removed member gives back only the agents on the same host; a refused one is in `stayed`.
- The killed agents of a removed member move to the heir only on the same host. The removal of an isolated member is refused until their OS user is turned off (2.3), and an heir is an owner, never isolated, so a removal never moves an agent between hosts.

While `member-os-users.json` is broken, every member counts as their own host, so every manager change between two members is refused until the file is repaired (fail closed).

The writers themselves (`OfficeState.updateAgent` for a live agent's `userId`, and the killed-agent history write) throw on a change between hosts, so a new path that skips the check fails at its first use.

Moving the agent and its files to the new host instead is task abdb452b.

## 3. Working together across users

### 3.1 What an isolated member can do to office-user agents

Nil, 2026-11-14, design ask f4e7bf5c, as recorded by Isomux PM in the task description: "Build it; the member loses reach over office agents."

**Owners cannot be isolated.** An owner sets office variables, which reach every office-user agent (`NODE_OPTIONS`, `LD_PRELOAD` or `GIT_CONFIG_*` would run the owner's code as the office user at the next spawn), and manages secrets, Integrations, other members and managers. The enable command and the Members page refuse an owner, and the office refuses to make an isolated member an owner until the owner runs disable.

The rule: no mechanical reach. An isolated member, their API tokens and their agents cannot:

- open a terminal on an agent that runs as the office user (that is a shell as the office user);
- change the folder, instructions, engine or schedules of an agent on another host, or set the folder of a room;
- make an agent that runs as the office user.

They still see those agents' chat and logs in shared rooms, and can message them. A message is the soft boundary of docs/isolation-model.md ("Agents of another member"): the agent treats it as data and confirms before it acts as its manager.

The other choice is that only the member's agents are isolated, and the member keeps the reach above. Then the member can read every office file through a terminal or a folder change, so the feature protects against the member's agents, not against the member.

As built (slice 2c, `server/identity/member-reach.ts`):

- The actor of a request is the member it acts for: the signed-in member, a token's member, the current manager of an agent (not the member who spawned it), a schedule's owner or an app's owner. An agent token whose agent is gone is refused on every limited route.
- Every API route and every WebSocket frame type has a rule, and a test fails when a new one has none. For an actor without their own OS user, every rule passes.
- On an agent that is not theirs, an isolated actor cannot open, save or watch a file, open a terminal, run an ask's command or a refused command, set instructions, access or Privileged, answer a prompt, or change any agent field except the name and the outfit. Their message to such an agent never answers its pending prompt (409 `awaits_member_answer`), also after an edit.
- An isolated actor cannot set a room's folder or a room's instructions, saves, makes and deletes only their own skills, through their runner (2d-iii-b), and makes or revives agents only for themselves.
- A moved agent takes the instructions of its new room. Room instructions that a member wrote before they got their own OS user stay in that room.
- Memory, tasks, messages and reads stay open: agents read them as data.

### 3.2 Shared folders

- **ACLs, not groups.** Groups need root, so agents cannot make them. The owner of a folder grants another user access with an access ACL and a default ACL (`setfacl -R -m u:<user>:rX,d:u:<user>:rX <dir>`; `rwX` for write) and `x` on each ancestor. The other agent adds the repo to its own `git config --global safe.directory`. No shared folder is imposed (Nil, 2026-11-14).
- **Read sharing is safe; write sharing with an office-user agent is not.** git config (`core.fsmonitor`, hooks), `.claude/settings.json`, package scripts and tests in a repo run as every user that works in it, and `safe.directory` turns off git's one guard. So when an isolated member can write a folder that an office-user agent works in, the member's code runs as the office user, and the isolation is gone for that member. Write sharing between two isolated members is fine: each can only reach the other.
- **System prompt.** Once one member has an OS user, every agent gets one line: share with ACLs; read sharing is safe; write sharing with an agent on another user lets that user run code as you. An isolated agent is told its user name.

### 3.3 An agent's folder that the new user cannot reach

The agent does not start there: its turn fails with the folder and the ACL command for read sharing, and the member or an office agent shares the folder or changes the agent's folder. The enable command lists these folders.

## 5. What stays open (residual risk, for the docs)

- The office user and its agents can read and act as an isolated member (accepted).
- A message to an agent that runs as the office user with a shell can ask it to read office files for the sender (soft, as today).
- Shared memory and skills that an isolated member writes are loaded by office-user agents; a skill can ship a script that an office agent runs (soft: the agent decides to run it).
- A loopback service of the office user without its own auth is reachable from any user on the box (for example a local database with trust auth on a dev box). The office's own services (the API, OpenCode serve, the secret proxy) check a token or password.
- With the Claude fallback on, the member's agents can read the office inference token (accepted, 1.6).
- The member's agents see other users' process lists, as today; each agent session has its own PID namespace on Linux.

## 6. Slices

Each slice keeps an office with no isolated member unchanged and is tested with the two-user container rig of the split design (scripts/split-rig.sh), changed to one office user and one member user. The server answers "not ready" to the enable command until slice 4.

1. **The runner per member.** `hostFor(userId)`, the runner bundle and its update, the unit template, `isomux-member-user enable/disable` and the `admin.sock` verbs, the file moves through the runner, the per-member trusted checks, the runner-reply rule (the `process.kill` audit), and Claude, Codex and OpenCode sessions (spawn, session store, resume checks) through the member's host.
   - Agent space: a member host's `agentRoot()` is `<member home>/.isomux-agent`, made by the runner as the member. Provider homes, the Codex home (always set for an isolated member), OpenCode profiles and the empty and one-shot folders go under it. A sync check of the office's files (`claudeSessionFileExists`, `isCodexAuthenticated`, `isClaudeCodeInstalled` and the rest) throws on an isolated member's env; the `OnHost` twin reads through their host, or a sync caller skips the check and lets the engine report a missing file. When the engine reports at resume that it has no stored conversation for the id (Claude's error result, Codex's thread/resume, OpenCode's 404), the office drops the id, as its own check does for an office agent, and a new conversation gets the waiting messages, once. A Claude session's root is searched through the host before the turn and pinned, so the env build only reads the pin; a pin outside the member's roots does not count.
   - The moves on enable and disable: the server reads files that the member's agents wrote as the office user, so it opens each with `O_NOFOLLOW`, takes only regular files with one link, walks with `lstat` without entering a linked folder, stays on one file system and keeps a size bound; it skips and logs anything else. Each open file is checked by `fstat` against the walk (same device and inode), so a folder swapped for a link after the walk is not followed. The Claude transcripts of the member's sessions move by session id (the exact file and the `<id>/` folder under each root searched before), with no folder scan. Pins and session paths change only after the runner confirms every file; an undo removes what the runner wrote, as the member, before the server keeps its own copy.
   - Parts: 1c-ii-a is the move on enable (2.2). 1c-ii-b is disable (2.3), the purge of a removed member through the runner, a member's cwd change (the Claude session files move in their runner, `claude-cwd-move`) and the OpenCode recovery between the member's two profiles through their host. Cron run sessions and their pins, apps and terminals move in slice 3.
2. **The fence, the reach and the share.** Every item of section 1.4, the limits of section 3.1 (terminals, agent and room edits, spawns), the member share (uploads, shown files, the Codex hook, the authority socket, the CA bundle) and secrets.
   - Already through the host before slice 2: the diff, the folder file tools, terminal spawns and ask command runs.
   - Parts: 2a is the files that an agent names: the editor (open, save, watch), read-file (also of a schedule run), the asks (probe, copy, in-place media with byte ranges), `/isomux-edit`, the app thumbnail `{path}`, Codex image views and generated images, and browser upload. 2b is the agent's folder (section 3.3) and the session reads: Claude fork and history, the Codex rollout walk, the OpenCode database check, the account and usage probes, and preview capture, whose browser runs as the member. 2c is the reach of section 3.1. 2d is the share and secrets (copies in the share: the member cannot read the code tree or `STATE_ROOT`), and the member's skill folder (in their agent space, written by their runner).
   - 2a rules: each read takes the host of the agent's manager as a required argument, so no caller falls back to the office's file system; the office host keeps its own code path. The host's fs has `stat` and `readBytes(path, max)`; the server counts the bytes of every runner reply against its own bound. Larger reads (in-place media, browser upload) stream through the `file-read` entry, which sends the realpath and size first; the server counts the bytes against the range it asked for, and a short stream fails the response.
   - 2d-i rules (the Codex safety hook): the hook is part of the member runtime, `runtime/<hash>/bin/isomux-codex-safety-hook` (a copy, 0755; the runtime hash covers its bytes), written by the runtime install. A member's Codex config names `<share>/runtime/current/bin/isomux-codex-safety-hook`, written in their Codex home by their runner, with Codex's trust hash measured by their runner. A member's Codex does not start when any step fails: no artifact, a hook file that is missing or has other bytes (after one reinstall of the runtime), the trust measurement, the config write or its reply. A runtime whose hook did not build is not kept, so the next start builds again. The office's Codex keeps its warning. For a member's Claude agent, the safety policy reads `~` as the member's home. A member's OpenCode needs no change: its plugin is built in the member's helper, and the office refuses every prompt until the plugin is active.
   - 2d-ii-a rules (the secret proxy and its CA bundle): the proxy ties each member OS user's uid to its member (`STATE_ROOT/member-os-uid-ties.json`, written before the record; a tie outlives disable, so a process of the uid that still runs keeps only its member's secrets). While any uid is tied, the proxy reads the peer uid of every `CONNECT`, with the password or without it; a failed lookup gets the 407. A connection from a tied uid swaps only office secrets and that member's: another placeholder, in any form, gets a 403 that names no secret, and nothing goes upstream. Without the password, a tied uid is served as the office's own uid is. A member's connect waits until the proxy child confirms a snapshot that holds the tie (5 s), else the member stays not ready. The share holds `secrets/ca-bundle.pem`, a copy of the office bundle (0644; written only when it holds certificates and nothing else) at each connect and when the office makes its bundle, and a member's CA variables name it. Until slice 3, a member's apps and schedule runs run as the office user, so they get the office's whole set.
   - 2d-ii-b rules (uploads and the authority socket): a member's agent gets each upload and screenshot as a copy in `<share>/files/<agentId>/<name>` (the name in `LOGS_DIR`; the folders get the setgid bit and the member's group only from the setgid share, since the office is not in that group and its chmod would clear the bit, so the files, 0640, have the member's group). The office writes it with the same no-follow, exclusive write as its folder copies; a failed copy is left out with a log line, and a failed screenshot copy is an error, never the office path. A member's agent below standard with a folder gets the copy in `<folder>/attachments/` from their runner (the `attachment-copy` entry copies the share file as the member, so no bytes cross the socket), and each send of that agent waits for the one before it. The copies go when the prune deletes the upload (also of a killed agent: every member share is tried), at disable and at a removed member's purge. A member's OpenCode calls the office through their own socket, `<share>/authority/authority.sock` (its folder made the same way, the socket 0660 with the member's group), which only their uid may use and which knows only their agents' turn handles; it closes at disable, and its file goes with it. The share check allows that one socket and no other.
   - 2d-iii-a rules (an isolated member's skills in their agents): the office never stats, reads or links a member's skill root, a plugin path their Claude reports or their synced folder with its own files. Their roots are their own homes (`memberUserSkillRoots`): no box root and no `STATE_ROOT/skills`. Their runner lists the user, plugin and synced skills (`user-skills`) and the project skills (`project-skills`), names and descriptions only, and reads one skill at its invocation (`user-skill`, then `project-skill`); the order stays user, project, bundled, synced. The runner reads as the member, so it reaches only what the member's own shell could, also when a reported path names an office folder. Every reply is member data: one entry out of shape or bounds refuses the whole reply, and a call that fails or does not answer in 30 s is one log line (menu) or one chat line (invocation). The lists are asked again at each refresh of the office's own lists (session init, spawn, restore, a skill saved, created or deleted, a plugin reload) and at each connect of the member's runner. Their skill folder is in their agent space, `skill-folders/<engine>/<key>`, built by their runner (`skill-folder`): the office sends their folders as strings and the bundled skills as bytes (at most 200 files, 256 KiB each, 512 KiB in all, checked on both sides), the runner writes the bundled skills to `skill-folders/bundled/<hash>` and keeps that copy and the one before it. A session gets the folder only after a build for its input answered, so a session that starts first (also a busy session resumed after a restart) runs without it until its next start; the menu and `/name` work meanwhile. One build per input runs at a time, and Codex reads the folder again only after the rebuild of a refresh answered. For a member, each `/name` that is no menu entry makes a runner call (up to 30 s) before the bundled read.
   - 2d-iii-b rules (the skills page of an isolated member): the side is chosen by the caller, not by an agent. Their catalog comes from their runner (`skill-catalog`): their own roots, their plugins and the folders of their own agents, read as the member; the office sends the built-ins as data (names and paths of our code) and fills in the use counts. The office checks each entry (names, sources, kinds, paths, sizes; a built-in only at a path it sent; only user and project skills editable): one entry out of shape refuses the whole reply. A path is found in that catalog exactly, never through the office's own links. Reads, saves, deletes and new skills go through their host as the member, with the editor's revisions (keyed by their host); only a built-in is read by the office (our code). A runner that is not connected gives 409 `member_os_user`, a failed or late call (30 s) 502. Every other caller's catalog leaves out the agents of isolated members: their folders are read only for that member, through their runner.
   - 2b-iii rules (preview capture): for an isolated member's agent, the pre-flight is the runner entry `url-probe` (the server checks its reply shape), and the browser runs as the member with its profile under `<agentRoot>/preview/<random>` (0700). The server reads the screenshot only with `readBytes` and the cap, stops the browser only with `signalGroup`, and removes the profile after the browser closed. Every capture, of the office and of a member, starts at a 0600 start page that holds the URL, so no URL (or app sign-in code) is in argv. Hosting, checked 2026-11-15: the container image (Debian chromium, its seccomp profile) in the member rig; the systemd shape by Reviewer 2 on auntie-2 (Ubuntu 24.04, `kernel.apparmor_restrict_unprivileged_userns=1`), where `systemd-run --user -p NoNewPrivileges=yes /usr/bin/google-chrome --headless=new --screenshot=...` captured through the namespace sandbox, as without NoNewPrivileges. Another distro's failure shows the browser's stderr; there is no office fallback and never `--no-sandbox`.
3. **Terminals, apps, schedules, backups, removal, manager change.** Apps under the member user's systemd manager (the runner env carries `XDG_RUNTIME_DIR`); the backup streams each member's agent space through its runner, with the usual credential exclusions; section 2.4.
   - Parts: 3d is the manager change (2.4, refused between hosts). 3a is schedules, 3b apps, 3c backups and removal.
   - 3a rules (schedules): an isolated member's session and command runs already start as the member (the run env is theirs, and the backends and the terminal panel pick their host). The checks around a run go through their host too:
     - A job's folder is stored with `~` and relative paths in the member's home (`resolveAgentCwd`), and the routes check it with a stat and an enter through their host. The folder rules (office state, overlap) compare the folder with its links resolved by their runner (`folderForRules`), or as written when the runner cannot resolve it, never by the office's realpath.
     - The limits on a schedule or a spawn that an ordinary agent makes (`folderInside`) resolve both folders through the host of the agent's manager (`AgentFs.realpath`, the runner's `realpath` call). A runner error or a host that is not ready is outside. A job and an agent on two different hosts are refused, with a log line.
     - The start of a session run: `fire()` records the run as running and holds a `preparing` slot, so a tick meanwhile records a skip and a send or an edit is busy. Then `startMemberRun` checks, through the host: the runner is connected (else the run fails with `startNotReady`), the folder, the limits, and the skill folder build (at most its 30 s bound; a run without it starts without the member's skills, with one log line). After each await it starts nothing when a delete ended the run or the server stops; the next boot ends such a row as `serverRestarted`. The office's runs keep their synchronous start, in the same order. A command run checks its limits and folder in its own async start.
     - A follow-up or an edit claims the run's slot first, then checks the folder through the host and pins the Claude session root found through the host; a refusal releases the claim.
     - The read-file of a run uses the office's fs only for the office's own local host.
   - 3b rules (apps): the office's supervisor is a router (`app-supervisor-router.ts`) that sends each app to the supervisor of its owner's host. An isolated member's app never goes to the office's.
     - A member's supervisor is the office's code with a host that is their runner (`member-app-host.ts`): the unit in their `~/.config/systemd/user`, the launcher, token and secrets files in `<agent space>/apps/`, the data in `<agent space>/apps/data/<name>`, and `systemctl --user` and `journalctl --user` run as them (only those two programs, with their `XDG_RUNTIME_DIR` and bus). Each call is a synchronous runner call (`agent-runner/sync_call.py`, which checks the listener's uid first), bounded at 5 s. A timeout or a dead socket opens a breaker: for 60 s every call for that member fails at once. On their host, start, stop and restart only queue the job (`--no-block`), and a teardown waits at most 2 s for a stop, then refuses (try again).
     - A runner that is not ready: 409 `member_os_user`, states `unknown`, and a delete refuses. An admin who cannot start it again disables with `--keep-files`; the apps are then office apps with no unit, stopped, and can be deleted. A member whose `systemctl --user show-environment` fails (no user manager: the container shape) gets 501 `apps_not_supported` from their own check, held 60 s. A delete asks again at once. When that fails too and their runtime folder `/run/user/<uid>/systemd` is absent (no manager runs), the delete removes the app's files on their host through the runner (unit, enable link, launcher, token, secrets), so a manager that comes up later starts nothing, and then the record. With the folder there (a bus that fails), the delete refuses (try again) and removes nothing. A delete of a member's app also removes what a failed move left on the office's host.
     - Enable and disable move the member's apps: the old host's teardown before the files move (a teardown that fails stops the move), their data moves with the other files, then the new host's install with a new token (the old one is never read back from the member's home) and the secrets from the store. An app starts again only when it ran; a stopped one gets its files and stays stopped. On the container shape the app stays registered and stopped, with a log line. A start or restart whose host holds no token that matches the hash provisions a new one first.
     - Before each relayed request (HTTP and each WebSocket upgrade, no cache) the office reads `/proc/net/tcp` and `tcp6`: every LISTEN socket on the app's port must belong to the uid that runs the app (the office's own uid on the systemd shape, the owner of the container supervisor's socket, the member's uid), and one must accept 127.0.0.1. Else 502, and the proxy secret is not sent. Office apps get the check too.
     - Cwd checks at register and at a cwd change run on the owner's host (`validateAgentCwd`, `folderForRules`). The boot passes (tokens, URLs, secrets, the stop of an app its owner's pack does not allow, the start of the apps a lock stopped) skip the apps of a member whose runner is not connected, with one log line, and run for them at their runner's connect, the starts last. The names of the apps a lock stopped that wait for a runner go to a file of their own, so a new lock's record never mixes with them.
     - A lock stops her apps through her runner, as the office's: the lockdown route through the office's router, and every locked boot (also after `isomux-rescue lockdown`) through a router of the locked office that calls her runner directly (`locked-member-apps.ts`: her record, her runner socket, and her home from passwd; the runner's `info` must name her uid and user; a sync call needs no office connect). A runner that does not answer at the locked boot is asked again every 60 s, one call bound per try, until her apps are stopped; those later stops are not recorded for the unlock, as the box boot may have started the app. `lockdown --stop` runs no locked office, so root stops her apps itself (`scripts/rescue-root.sh`, task 367596bc part 2): it turns her linger off, so no boot starts her user manager, and stops `user@<uid>.service`, for each OS user whose `.env` names this office's uid. It records first, in `/etc/isomux/lockdown-members`, the users whose linger it turned off, and the unlock turns their linger on again, only for a user still of this office; a failure names the `loginctl enable-linger` command to run. The host step `lock-effects` leaves her apps out: they are not units of the office's manager. Her units are never disabled at a lock (the office's are, task 367596bc): an enable that fails at the unlock would leave her app off for good, and each locked boot stops what her manager started. In the container, `lockdown --stop` takes the container down (`docker compose down`, restart "no", the unit disabled): every app and runner in it ends and nothing starts at a boot, and member apps are not supported there. Against her will the stop is best effort: while her manager lingers, she can start a process of her uid herself.
     - Not verified across two uids (no root on the test box): linger, a second uid's bus, and `journalctl --user` for a member, which shows their journal only when the journal is persistent (`SplitMode=uid`); with volatile storage their logs are empty, with no error. Checked on auntie-2 (2026-11-16) against the office user's own manager: install, state, logs, the port check (and a refusal for another uid's socket), teardown and the breaker, all through the runner.
   - 3c rules (backups): each copy also holds the agent space of every isolated member, beside the state root and never inside it: `members/<userId>/` with `member.json`, `space/` (files only) and its manifest (`member-backup.ts`). The copy's top level is fixed, and a reader treats only the state root as office state.
     - The member's runner lists their space (`backup-list`) and sends the files asked for (`backup-files`), as them. One matcher (`member-space-exclusions.ts`), imported by the runner and by the office, leaves out what the office's backup leaves out (credential and secret stores with the office's globs, backend login names at any depth, the regenerable locations segment by segment, so a `cache` folder deep in their data stays) and their own: `apps/units`, `apps/secrets`, the move staging folders, `preview` and `skill-folders`. The office checks every listed path again.
     - The office trusts only the bytes: each path normalised, listed once, under a listed folder; each file written `O_EXCL|O_NOFOLLOW` 0600 in folders the office made, never more bytes than listed; links only in the manifest; sockets, FIFOs, devices, files over the move's file bound and files that changed inode or shrank are counted and named in `member.json`.
     - Nothing of theirs fails the office's copy. Their part runs after the office's copy is written and verified, each member checked for free space alone; a member who is not ready, does not fit, goes over 10 min or 60 s without a byte, sends a bad stream or does not verify is carried: their tree of the newest copy that has one is hard-linked in, and `member.json` names the copy where it was made (`carriedFrom`, `copiedAt`). With no tree to carry: `skipped`, `member.json` only. `backup.json` lists every member not copied in the run (`membersSkipped`), and the status gives their names.
     - Unchanged files are hard links to the previous tree, as for the state root.
     - Removal adds nothing: the removal of an isolated member is refused until their OS user is turned off, which brings their files and apps back first.
4. **The product.** The Members page, the office fallback (the Claude token and its expiry page, Codex off), the system-prompt lines, routes for the two agent-reference pages that tell agents to read `~/.isomux` files (discovery, cronjobs), the docs (docs/isolation-model.md, docs/security-audit.md, docs/access-and-invites.md, docs/hosting-reference.md, docs/features.md), and the switch that lets the enable command run.
