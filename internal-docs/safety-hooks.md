# Agent safety hooks

Isomux applies the same safety policy before recognized tool calls from Claude, Codex, and OpenCode agents. The policy blocks recognized destructive commands, protected-path writes, secret-bearing reads, reads of another process's environment, cross-agent process kills, commands that open outbound tunnels, and recognized uses of the admin socket (`admin.sock`, `admin-cli`, `owner-login`), which mints owner sign-in links.

These checks reduce accidents by honest agents. They are not complete prevention, and they are not an operating-system security boundary.

## Security boundary

In a standard Isomux install, the server, its agents, and the Codex checker run as the same operating-system user. File mode bits can exclude other users, but they do not isolate processes that share that user ID. An agent that acts adversarially with the same user permissions can change files that the server can change. Stronger isolation requires running Isomux under a dedicated operating-system identity, separate from the owner's account, and may require stronger isolation between agents.

A filesystem-capable MCP remains a concrete route around the built-in tool mappings. On 2026-08-30, live policy checks allowed such an MCP to write Isomux state, read a backend login file, and replace the Codex checker executable. Mapping Codex `apply_patch` into the safety policy closed that tool route; it did not close the class of filesystem-capable tools.

The agent browser (`server/browser-actions.ts`, `server/browser-extension-session.ts`) controls a tab explicitly offered by its manager in the paired Chrome extension. The server checks manager and room access, generation and assignment ownership. Navigation accepts HTTP(S) without URL credentials. Uploads use the shared sensitive-file policy before sending file bytes. Browser APIs are not backend tools, so backend hooks do not see them. The manager's existing logins increase what an agent or hostile page can reach; the manager-login confirmation rule still applies. Off, expiry and connection loss release control. Server interactive profiles and the remote Browser panel are retired; saved profile files remain unused. Screenshot previews still run separately on the server.

Before each Codex spawn, Isomux hashes the installed checker bytes and repairs missing or changed content from a verified build artifact. However, a replacement at the same path can affect the next tool call in an already running session. The pre-spawn repair therefore limits a replaced checker to the remainder of the current session; it does not protect that live session.

## Protected paths and limits

Protected write targets resolve against the agent working directory. When a hook input has no non-empty absolute working directory, a relative target with a bounded `.isomux` path segment denies, while an ordinary relative target remains allowed. The residue is that an ordinary relative target can fail open if the provider stops sending the working directory and the agent is already working inside the state root. Codex emits a transcript warning on every tool call with a missing or invalid working directory, so this reduced coverage is visible rather than silent; the parser test does not prove that a future Codex version will keep sending the field.

The shell check tracks the possible working directories on command success and failure. `cd X && W` checks W in X; `cd X || W` checks W in the original directory; `cd X ; W` and a newline check both. A write denies if any possible directory resolves its target into the state root. Subshells, command substitutions, background jobs, pipeline elements and `bash -c` payloads inherit the parent directory and cannot change it. `eval` runs in the current shell, so a cd in its payload moves the directory; an `eval` with an expansion in its words, or one nested past the depth limit, makes the directory unresolved. A literal absolute or `~/` cd target can establish the directory even when the envelope has no cwd. When the line names `CDPATH` or `cdable_vars`, a relative cd target is unresolved unless it is `.` or `..` or starts with `./` or `../`. CDPATH set in the agent's environment and not on the line is not seen. Shell forms outside this control grammar, such as function definitions in either form, keep relative writes unresolved only when the parsed words include `cd`, `pushd`, `popd` or `eval`, quoted or not. This conservative check does not depend on a shell-keyword list. Unsupported syntax alone keeps the parent directories. The parser and flow traversal use stacks so large command lists and nested groups do not exhaust the checker.

An unresolvable directory-change operand denies later relative writes on that branch. The message names the shell directory change, rather than claiming the envelope omitted cwd. A genuinely missing or invalid envelope cwd keeps the existing message and protected-candidate rule. A quoted flag counts as a flag when the check finds write targets, because the program reads its options after the shell removed the quotes: `sed '-i'` and `perl '-pi'` edit in place. A non-literal write target with a bounded `.isomux` segment also denies, with a message naming the non-literal target; the segment check splits on path and quote delimiters, so `"$(echo ~/.isomux)/x"` denies.

The shell check follows variables set on the same line (task 7ea62548): bare, `export`/`declare`/`local`/`readonly`/`typeset`, command-prefix (also passed on by `env` or `sudo`) and array assignments, and `for`/`select` loop words, nested `bash -c` and `eval` payloads included. Each name keeps every value it gets on the line, because scope (subshells, `||` branches) is not modeled: this fails closed, and a reassignment never clears a state path. A write target is checked with each reference expanded; a result that resolves into the state root denies with the state-root message, and one that stays non-literal goes through the segment check. A name set by `printf -v`, a nameref (`declare -n` and its siblings), a `${!ref}` indirect expansion, or more than 32 values or combinations denies as non-literal. `STATE_PATH_VARIABLES` lists the variables Isomux sets to state paths (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, the CA-bundle variables, OpenCode's `XDG_*_HOME`): a write target that names one denies whatever follows it, while reads through them stay allowed. `STATE_PATH_EXCLUSIONS` keeps `HOME` and `TMPDIR` out, with the reason; a test asserts every variable the server sets at or below the state root is in one of the two lists. A variable path outside the state root stays allowed: this is not a general ban on variable paths.

A leading `~` and `$HOME` in a write target resolve from the shell's home and from every value `HOME` gets on the line, on every engine, so `HOME=~/.isomux; touch ~/x` denies (task fc942b38). The shell's home is the real home, except in an OpenCode shell: there `HOME` and `TMPDIR` are the profile's `home` and `tmp` folders under the state root, and the safety plugin passes them in the policy context (`shellHome`, `shellTmpDir`). Those two folders are the agent's own space and stay writable from the shell and the file tools; the rest of the profile, and every other path under the state root, still denies, also through `~/..` or `$TMPDIR/..`. A value at or above the state root opens nothing. Reads still resolve `~` to the real home.

`find` is judged as the commands it runs (task 230d4a04). Each `-exec`, `-execdir`, `-ok` and `-okdir` list, up to `;` or a `+` right after `{}`, is a command of its own for every shell check, as a `bash -c` payload is. `{}` is checked once as each start path and once as a path below it, because either can be the one a write or read lands on. A `-execdir` list resolves relative targets in each start path and in the directory that holds it, where it runs for the start path itself; a `..` target from a deeper subdirectory is not seen. `-delete` makes each start path a write target, and `-fprint`, `-fprint0`, `-fls` and `-fprintf` make their file one. A start path above the state root is not a write to it, as for `rm -r`: `find ~ -name x -delete` stays allowed. One shell line expands to at most 256 runs and 32 KB of run text, across nested finds and `bash -c` payloads, because every check parses each run again; past either bound the line denies as non-literal. Start paths read from `-files0-from` are not seen.

The hook cannot see a write made inside an interpreter body or a script (python, node, sqlite, a heredoc fed to one), a variable set in an earlier call or a sourced file, or one filled by `read` or `mapfile`. It does not follow symlinks, so in an OpenCode shell `ln -s ~/../data ~/d; echo > ~/d/x` writes profile data. The system prompt and the state-root refusal tell the agent to stop and ask the member instead of reaching a refused target another way.

On 2026-09-07, the verbatim catalog input from task f9a24bf9 reproduced the false denial with both a valid and an empty envelope cwd. Both provider adapters already forwarded cwd. The policy discarded that value because its raw control regex matched parentheses in the quoted heredoc. The same regex treated the ampersand in `2>&1` as background control. The policy now uses the parser's quote-aware control metadata. The tests also close the failed-cd sequence case (the write after `cd /safe ;` can still run in the original directory) and the previously allowed `cat > "$HOME/.isomux/x"` target. `server/safety-policy-cwd.test.ts` holds the command-shape cases; `server/test-support/fixtures/safety-hook-cwd-catalog.json` preserves the task input.

The destructive-command patterns run on each command of a shell line, as the command parser splits it: on `;`, newlines, pipes, `&&`, `||`, a background `&`, subshell parentheses and command substitutions. One destructive command denies the line, so `git checkout -b x && git reset --hard` denies. The parser also yields the commands inside a `bash -c` (or `sh -c`, `eval`) payload and inside a substitution in double quotes, and resolves quotes, escapes and `$'…'` in each word, so `bash -c 'git reset --hard'`, `echo "$(git reset --hard)"` and `git reset "--hard"` deny. Git options before the subcommand (`-C <dir>`, `-c <key=value>`, `--git-dir`, `--no-pager` and the rest) are skipped, so `git -C dir reset --hard` denies like `git reset --hard`. A word that holds whitespace is one argument and matches no pattern, so quoted prose stays data. The `rm` temp-directory exception applies only when every operand names one entry directly in `/tmp` or `/var/tmp`, as written: `rm -rf /tmp/a` is allowed, while `rm -rf /tmp/a/b`, `/tmp/a/` and `/tmp/a/*` deny because a deeper path can pass through a symlink. The policy does not stat the disk, because the command itself can create the link first. `$TMPDIR` has no exception, because it is usually unset and `$TMPDIR/home` then names `/home`. `server/safety-policy-segments.test.ts` holds the cases.

Relative paths that resolve under the literal `~/.isomux` are mapped to the configured state root before the boundary check. This is an identity in a default install. With a non-default state root, it also denies writes to the literal `~/.isomux` path. The missing-cwd candidate rule recognizes the literal `.isomux` segment only, so under a non-default state root it does not recognize that root's own basename - a third-order fail-open needing both a missing working directory and a non-default root.

Another process's environment (`/proc/<pid>/environ`, `/proc/<pid>/task/<tid>/environ`, `ps e`, `ps -E`) holds other agents' office tokens and secret placeholders, because all agents share one OS user. The check reads every word of a shell line, assignments and input redirections included, and the file-read tools' paths. A word denies when, after brace expansion, globs and resolution against the working directory, it could name such a file for a pid other than `self`, `thread-self`, `$$`, `$BASHPID` or `$!`; a `/proc/<pid>/root` prefix is followed. The own pid is decided from the text only: the policy has no process to anchor a tree walk (Claude's hook runs in the server, and one OpenCode server serves many agents), so a literal pid of the agent's own child denies. A recursive search rooted at `/` or at or below `/proc` denies, because `grep -R` follows `/proc/self/root` back to `/`. An interpreter, a script or an MCP server still reads the file; `server/safety-policy-environ.test.ts` holds the cases.

## Measured coverage

OpenCode 2.1.4 emits an authoritative `permission.asked` event before an asked tool call runs. Isomux maps the shell command and the edit's files from it, evaluates the neutral policy in-process, and answers `once`, or `reject` with the reason, which fails only that tool call. Interactive default mode still asks the member after a safe policy decision. Bypass and cron modes answer safe shell and edit calls once without a member prompt. The cron agent denies the subagent tool; interactive bypass allows it, and the transport answers a subagent session's requests as the agent's own. Read and grep emit no permission event. The Isomux safety plugin checks every shell, read, grep, edit, write and patch call in its `execute.before` hook as well (`opencode-oc1-scope.md`).

The Codex hook contract was measured with Codex 0.144.6 on 2026-08-28 and 2026-08-29. `PreToolUse` covered every measured Bash, `apply_patch`, dynamic-tool, and MCP action before its side effect. Fresh, resumed, forked, and one-shot sessions were measured directly. Cron runs and model listing use the same spawn path, so their setup coverage is inferred rather than measured with a tool action.

`PermissionRequest` added no tool coverage in the measured `never` and `untrusted` approval modes. Under `never`, only `PreToolUse` fired. Under `untrusted`, the measured action reached `PreToolUse` first and `PermissionRequest` second. This conclusion applies only to those measured modes.

On 2026-08-29, the production installer was proven end to end for the allow arm: it installed and trusted the hook, the hook ran and returned a decision, and the allowed command completed. The installed hook's own deny was not observed end to end because the model declined to issue the protected command. The deny claim is a composition: the production installer was shown to create the trusted decision path, and the 2026-08-28 hook-contract measurement showed that a trusted deny blocked the action in both measured runs. The link between those measurements is inferred.

On 2026-10-02, the trust pin (`CODEX_HOOK_TRUST_HASH_PROVEN_VERSION`) moved to Codex 0.160.0. The live trust contract test showed the installer hash equal to Codex's `currentHash`. The paid pair allowed the workspace write and blocked the protected write on both gpt-6.1-sol and gpt-5.6-sol. The coverage matrix passed on gpt-5.6-sol. On gpt-6.1-sol, every action the model issued got the expected hook result, but in 4 of 31 cells the model issued no tool call.

On 2026-10-25, the trust pin moved to Codex 0.164.0, with an API-key login. The live trust contract test showed the installer hash equal to Codex's `currentHash`. The paid pair allowed the workspace write and blocked the protected write on both gpt-6.1-sol and gpt-5.6-sol. The coverage matrix passed on gpt-5.6-sol with no validation error, and the model issued the tool call in all 31 cells.

## Failure behavior

Codex fails open when a hook executable is missing, exits with an error, times out, or returns an invalid result. Isomux surfaces the same signed transcript warning when it detects a pre-spawn installation or trust failure, a caught checker fault, or a technical `hook/completed` failure:

> Isomux safety check skipped: Isomux could not run its safety check on this tool call, so the call ran unchecked. Tell the office owner and check the isomux service logs.

The Codex session still starts after a pre-spawn failure. Isomux also writes a cause-specific server error so the office owner can distinguish artifact, repair, hook configuration, trust, and unexpected failures.

OpenCode also fails open when a permission envelope no longer matches the pinned contract or its adapter throws. Isomux answers the owned request once and puts the same warning in the transcript, at most once per turn. The agent then works without Isomux enforcement. That degraded state is the OpenCode coverage that existed before this adapter, so it is not a regression from the prior status quo. A real policy denial still rejects the call.

An event without a permission request id is different: Isomux cannot answer it without guessing ownership. It shows a transport warning and fails the turn instead of claiming an allow or leaving the turn parked. A malformed event is isolated from later valid events.

## Trust and event identity

Codex uses two numbering systems for hooks. A trust key uses the matcher-group index plus the hook's index within that group. A `hook/completed` event uses `displayOrder`, the flat handler position across all `PreToolUse` groups. These values are equal in layouts with one hook per group, which can hide an incorrect implementation. Isomux keeps them separate so a failed Isomux hook produces the safety warning without mislabeling a user's failed hook.

On 2026-09-04, a Codex 0.144.6 `hooks/list` probe put the same command in two matcher groups and returned the same `currentHash` at both positions. Changing the matcher string changed the hash. This shows that the trust hash binds to the matcher and command, not the positional trust key, so Isomux can rename a user's trust key when a removed group shifts its position.

Before each Codex spawn, Isomux replaces the first matcher whose command basename is `isomux-codex-safety-hook` and removes later Isomux matchers. The merge removes every trust sub-index at their pre-merge positions, including records without the Isomux sentinel, and renames every trust key for a shifted user group in one pass. It does not remove or rename a detached or out-of-range key. User trust block bodies stay unchanged.

The last Isomux process to merge wins. A process with a foreign state root replaces the single matcher with its own hook path. If that temporary path is later removed, the file can name one missing hook until an office Codex process spawns and repairs it. Sessions that are already running do not re-run the pre-spawn repair.

## Boot trust probe

At boot, Isomux starts a scratch Codex App Server without authentication and asks `hooks/list` for the trust hash used by the bundled Codex version. The complete scratch measurement, including process start, initialization, and `hooks/list`, has a 10-second deadline. On 2026-08-29, full boot preparation including compilation, closure analysis, source-stamp verification, and the trust measurement took about 2.41 seconds, so the deadline has about four times the observed headroom. If boot-probe timeouts appear in the server logs, this deadline is the first constant to inspect.

A failed trust measurement is not cached for the process lifetime. The office continues to listen, and each later Codex spawn retries the complete bounded measurement. If it still fails, the Codex session starts with the signed transcript warning.
