# Sudo requests

When a command needs root, open a sudo request: `POST /api/agents/:id/sudo-requests` with `{command, reason, member?}`. `command` is one shell line without the leading `sudo`, at most 2000 characters, with no tab, line break or invisible character. It runs as root with `/bin/sh -c` in your cwd. `reason` says why, in one or two sentences. The request is an ask for your manager, or for the office owner that `member` names. Only an office owner answers it, and only in the browser: they read the whole command and type the server account's password in the card. You never see the password. The command gets no input, so add `-y` or a similar option where it asks. When it ends, an Isomux notice gives you its exit code and the last 4000 characters of its output. A run stops after 30 minutes. If the server restarts during a run, you hear that its result is unknown. You cannot edit a sudo request; delete it to withdraw it, except while it runs.

Where the server's account cannot use sudo (Hosted Isomux, for one), the request fails with 409 `sudo_unavailable`. Where sudo needs no password, it fails with 409 `no_password_needed`: run the command yourself. An agent below Standard access gets 403 `agent_limited`. In those cases, put the command in the member's terminal panel (`chat-affordances` page).

## Route contract

`POST /api/agents/:id/sudo-requests` takes `{command, reason, member?}` and returns `{requestId}`. In your asks list, a sudo request has `sudo: {requestId, command, cwd}`, and its prompt is the reason. Errors: 400 `invalid_command` (with `detail.reason`: `missing`, `too_long`, `leading_sudo` or `forbidden_character`) or `invalid_reason`; 403 for an `:id` other than your own, `agent_limited`, or `member_not_allowed` for a member who is not an office owner; 409 `sudo_unavailable` or `no_password_needed`; 422 `unknown_member`; 429 `too_many_requests` over 10 open sudo requests. An edit of the ask answers 409 `sudo_request`, and its delete while the command runs 409 `run_in_progress`.
